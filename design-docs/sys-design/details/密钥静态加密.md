# 密钥静态加密（DB 落盘加密）

> 机制落地文档（基于实际代码）。变更说明见 `design-docs/modifications/2026-10-05-db-encryption-at-rest/`
> 与 `design-docs/modifications/2026-10-10-reencrypt-sweeps-list-endpoint/`（GET 列表端点）；
> 接口契约见 `api-define/OpenAPI接口定义/security.md`。

## 1. 机制定位

控制面库内两类密钥的落盘密文化：`providers.api_keys`（上游厂商密钥池，整列 JSON 信封）与
`api_keys.api_key`（下游虚拟密钥，单值信封）。定位是**防泄漏**（库文件/备份/从库介质），
不是防篡改（GCM 单值完整性仅防磁盘位翻转）。

## 2. 代码结构（实际实现）

| 文件 | 内容 |
|------|------|
| `lib/xcrypto/envelope.go` | `enc$v1$<base64(keyID(1B)\|nonce(12B)\|ct)>` 信封；`Encrypt/Decrypt/IsEncrypted/KeyIDOf` |
| `lib/xcrypto/keyring.go` | keyring 文件加载（TOML：`ActiveKeyID` + `[Keys]` map）；HKDF 派生 `db-enc-key`；`Encrypt` 用 active、`Decrypt` 按密文 keyID 查表、明文直通；`KeyHash`（见 §5） |
| `stateful/security.go` | `[Security]` 配置（`MasterKeyFile` 唯一注入方式，无 env）；`LoadSecretRing`（启动 fail-fast）；`/reload/security` 热加载（atomic 替换、失败保留旧 keyring）；`CheckSecretAtRest`（库有密文但无 keyring → 拒启动）；`EncryptIfEnabled/DecryptIfEnabled` |
| `storage/rdb/provider` | `api_keys` 列：写路径 Marshal→Encrypt；读路径 Decrypt→Unmarshal（`fromDAO` 返回 error，密文不传播） |
| `storage/rdb/api_key` | `api_key` 列同上；同事务写 `api_key_hash`；`APIKeyFilter.Key` 在 storager 层转 hash 查询（model 零改动） |
| `storage/rdb/keyrotate` + `model/keyrotate` | sweep 管理器：任务表 + 单行锁表（触发互斥/失联接管）、主键游标分批、双模式（reencrypt/decrypt）、dry-run、心跳进度 |
| `endpoints/openapi_v1/security` | `POST /open-api/v1/security/reencrypt-sweeps`（触发，202 异步）、`GET /security/reencrypt-sweeps`（历史列表）、`GET /security/reencrypt-sweeps/{task_id}`（查询；FeatureSecurity；列表与 `created_by` 为 2026-10-10 新增） |

## 3. 关键设计点

1. **解密选钥自描述**：密文首字节 keyID → keyring 查表；轮换并存期同表多 keyID 混存，无需任何外部映射；前瞻兼容按类别分钥（1 字节 255 空间，解密路径零改动）。
2. **marker 兼容**：无 `enc$v1$` 前缀 = 存量明文，读直通/写加密——不停机迁移、灰度与回滚天然安全。
3. **keyring 文件唯一注入**（评审决议，无 env）：0600、与数据目录异机；任何部署天然具备多钥 + 热加载完整轮换能力。
4. **DAO 边界透明**：model/endpoints 全程明文；InnerAPI 导出（mod-api-key 等）自动获得解密后数据。
5. **启动 fail-fast**：`main.go` 在 `rdb.Init` 后执行 `CheckSecretAtRest`——库有密文但 keyring 缺失/错钥 → 拒启动；无密文无 keyring → 渐进启用。

## 4. 轮换与收敛（强制，无自然收敛）

- **六步 runbook**：生成新钥 → keyring 追加 → 切 `ActiveKeyID` → **`/reload/security` 热加载（硬性要求，免重启）** → **触发 sweep（先 dry-run 并核对响应 `active_key_id`）** → 收敛完成后摘旧钥。
- **sweep = 唯一收敛机制**：冷数据行不触发写就永不重加密（评审指正）。`mode=reencrypt`（默认，收敛到 active 钥）/ `mode=decrypt`（仅回滚预案：原地解密、免导入恢复）。
- **多实例**：任务状态在 DB（`keyrotate_sweep_tasks` + 单行锁表 `keyrotate_sweep_lock`），触发与查询可跨实例；锁行 `FOR UPDATE` 串行化触发；心跳超时 5 分钟判定失联、自动接管（任务幂等）。
- **执行语义**：主键游标分页 100 行/批；每批一个事务（重写 + 进度心跳同事务提交）；批级死锁退让重试（业务优先）。

## 5. 实现校准记录（设计 vs 实际）

1. **`api_key_hash` 的 pepper 改为应用级常量**（原设计：keyring 锚定派生）：hash 是按值查询索引而非口令存储，api key 为 128bit 随机值，抗彩虹表靠熵而非 pepper 保密；常量 pepper 使哈希**完全不随 keyring 轮换变化**（锚定方案在摘锚钥后会失稳），且 keyring 文件校验少一条锚定约束。
2. **sweep 进度写入为批内 best-effort defer**：AddProgress 失败不回滚已重写行（进度精确性让位于数据正确性）。
3. **任务记录放 DB 而非 Redis**（评审决议）：低频 + 审计留存 + 不新增 Redis 依赖。
4. **validation 踩坑复用**：本模块再次验证"嵌套 struct 切片需显式 `dive`"（`keyringFile.Keys map` 无嵌套 struct，未踩坑；记录备查）。
5. **sweep 任务补充 GET 列表端点**（2026-10-10，`modifications/2026-10-10-reencrypt-sweeps-list-endpoint/`）：历史任务此前只能按 `task_id` 查询（ID 仅触发响应出现一次），新增 GET 集合端点（`status`/`mode`/`scope`/`dry_run`/`started_at` 区间过滤 + `page`/`page_size` 分页，默认 `started_at` 倒序）；任务对象对外暴露 `created_by`（库列本已存在，仅未暴露）。运行中任务以库内已落库值为准：`summary`/`duration_ms` 完成时才写入（running 时为空对象/0），dry-run 成功任务 `error="dry_run"`。

## 6. 可观测与失败语义

- 指标（8284 端口）：`crypto_decrypt_fail_total{table,key_id}`、`crypto_sweep_total{table,action}`、`crypto_sweep_running`。
- 解密失败：读路径 DAO 错误 → 5xx；日志只记 keyID/长度，密文不落日志；sweep 中单行解密失败 → 任务 failed。
- 热加载失败（格式错/ActiveKeyID 无对应条目）：返回错误，旧 keyring 保持生效。

## 7. 边界与已知限制

- 下发给 BFE 的配置文件加密（数据面磁盘）**另行立项**（本机制只管控制面库）。
- KMS/Vault 集成 = 商业版（`MasterKeyProvider` 接口预留）。
- `users.password` 明文 = 口令散列化关联项（bcrypt，单独立项）。
- `keyID=1` 的 master key 若需轮换（pepper 常量方案下）不影响 hash；但仍需 sweep 重加密存量密文。
