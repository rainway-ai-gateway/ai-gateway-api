# 路由规则管理

## 1. 概述

AI 网关存在两类路由规则：

1. **产品级路由规则（Product Route Rules）**：由 BFE 原生路由模型承载，基于域名、路径、HTTP 方法、Header、BFE 条件表达式等将流量分发到不同的 Cluster。
2. **AI 路由规则（AI Route Rules）**：统一存储在 `route_rules` 表中，面向 API-Key / Entity / Global 三级，决定命中某条 API-Key 后，请求应转发到哪个目标模型与集群，支持权重分流与 Fallback。`/ai-route-rules` 模块已从 OpenAPI 中移除，AI 路由规则不再按产品线独立维护。

本文档重点描述第二类 `route_rules` 的管理机制、层级绑定与导出逻辑；产品级路由规则作为流量入口，也会做简要说明。

---

## 2. 核心概念

| 概念 | 说明 | 数据载体 |
|------|------|---------|
| Product Route Rule | BFE 层路由规则，按域名/路径/表达式选择 Cluster | `model/iroute_conf` |
| AI Route Rule | AI 层路由规则，按条件选择目标模型与集群 | `route_rules` 表 |
| Route Table | 一组 AI Route Rule 的集合 | `route_rules` 表的一行 |
| Global Route Table | 全局默认路由表 | `route_rules` 表中 `type=global, owner=global` |
| Entity Route Table | Entity 级路由表 | `route_rules` 表中 `type=entity, owner=<entity_id>` |
| API-Key Route Table | API-Key 级路由表 | `route_rules` 表中 `type=api_key, owner=<api_key_id>` |

---

## 3. 产品级路由规则（BFE 入口路由）

### 3.1 职责

产品级路由规则负责把外部 HTTP 请求映射到 BFE 的 Cluster，是 AI 网关流量的第一层分发。它不关心 API-Key，只关心：

- 请求 Host
- 请求 Path
- HTTP Method
- Header
- BFE 条件表达式（如 `req_host_in("api.example.com")`）

### 3.2 数据模型

```go
type BasicRouteRule struct {
    HostNames []string
    Paths []string
    ClusterName string
    Description string
}

type AdvanceRouteRule struct {
    Name string
    Description string
    Expression string
    ClusterName string
}
```

### 3.3 条件表达式构建

`model/iai_route/ai_route.go` 提供了一套辅助函数，用于把高层语义转换为 BFE 条件表达式：

```go
func BuildAIRouteCond(ctx context.Context, basicInfo *BasicInfo) string
```

支持的条件维度：

| 维度 | BFE 条件函数示例 |
|------|-----------------|
| 域名 | `req_host_in("api.example.com")` |
| 路径前缀 | `req_path_prefix_in("/v1/chat", true)` |
| 路径精确 | `req_path_in("/v1/chat/completions", true)` |
| 路径后缀 | `req_path_suffix_in("/completions", true)` |
| HTTP 方法 | `req_method_in("POST")` |
| Header 前缀 | `req_header_value_prefix_in("X-Model", "gpt", true)` |
| Header 精确 | `req_header_value_in("X-Model", "gpt-4", true)` |
| Header 后缀 | `req_header_value_suffix_in("X-Model", "-4", true)` |
| 请求体 JSON | `req_body_json_in("model", "gpt-4", true)` |
| 请求体 JSON 前缀 | `req_body_json_prefix_in("model", "openrouter/", false)` |
| 请求体大小（大于） | `req_body_larger_than(8192)` |
| 请求体大小（小于） | `req_body_less_than(2048)` |

多个条件通过 `&&` 组合。

> 说明：`req_body_larger_than` / `req_body_less_than` 基于 HTTP `Content-Length` 头判断请求体字节数，单位：字节；无 `Content-Length` 时该条件不匹配。

### 3.4 导出

产品级路由规则通过 `RouteRuleManager.ExportRouteRule` 导出为：

- `host_table.json`
- `route_table.json`
- `cluster_conf.json`

> 具体导出格式遵循 BFE 原生配置规范。

## 4. AI 路由规则数据模型

### 4.1 表结构

```sql
CREATE TABLE route_rules (
    id BIGINT AUTO_INCREMENT PRIMARY KEY,
    type VARCHAR(64) NOT NULL COMMENT 'global / entity / api_key',
    owner VARCHAR(255) NOT NULL COMMENT '全局写 global，Entity 写 entity_id，API-Key 写 api_key_id',
    enabled TINYINT(1) NOT NULL DEFAULT 1,
    rules JSON NOT NULL COMMENT '规则数组',
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    UNIQUE KEY uk_route_rules_type_owner (type, owner)
);
```

### 4.2 规则 JSON 结构

```json
[
    {
        "name": "rule-1",
        "Cond": "req_body_json_in(\"model\", \"gpt-4\", false)",
        "targets": [
            {"ClusterName": "cluster-openai", "Model": "gpt-4", "Weight": 80},
            {"ClusterName": "cluster-azure", "Model": "gpt-4", "Weight": 20}
        ],
        "fallbacks": [
            {"ClusterName": "cluster-fallback", "Model": "gpt-3.5-turbo"}
        ]
    }
]
```

### 4.3 Go 模型

```go
// model/shared/types.go

type AiRouteRuleParam struct {
    Name *string `json:"name"`
    Cond *string `json:"Cond"`
    Targets []*AiRouteTargetParam `json:"targets"`
    Fallbacks []*AiRouteFallbackParam `json:"fallbacks"`
}

type AiRouteTargetParam struct {
    ClusterName *string `json:"ClusterName"`
    Model *string `json:"Model"`
    Weight *int `json:"Weight"`
}

type AiRouteFallbackParam struct {
    ClusterName *string `json:"ClusterName"`
    Model *string `json:"Model"`
}

type RouteRulesParam struct {
    ID *int64 `json:"id,omitempty"`
    Enabled *bool `json:"enabled"`
    Rules []*AiRouteRuleParam `json:"rules"`
}
```

## 5. 校验规则

路由规则的输入校验分两层，OpenAPI 写路径以端点层为准：

**端点层 `lib/validate.RouteRules`**（api-keys 创建/更新 `endpoints/openapi_v1/api_key/checker.go`、entities 创建/更新 `endpoints/openapi_v1/entity/validator.go`、Global 路由表更新 `endpoints/openapi_v1/global_route_rules/endpoints.go` 调用）执行完整校验，任一违反返回 422 `Param Illegal`：

1. **规则名称必填**且在同一张路由表中不能重复；
2. **条件表达式 `Cond` 必填**，且须为合法 BFE 条件表达式；
3. **`targets` 不能为空**；
4. **每个 target 必须有 `Weight`**，取值范围 [0,100]；
5. **所有 target 的 `Weight` 之和必须等于 100**；
6. **target 的 `ClusterName` 必填**，须符合 ClusterName 格式；
7. **target 的 `Model` 非空时**须符合模型名称格式；
8. **同一规则 `targets` 内 `(cluster_name, model)` 组合不能重复**（`model` 按最终值比较，空串与未填写等价）；
9. **Fallback 的 `ClusterName` 必填**且格式合法，**`fallbacks` 内 `(cluster_name, model)` 组合不能重复**；`fallbacks` 与 `targets` 之间允许重复（fallback 指向主 target 属合理降级配置，不做跨组判重，见 `api-define/OpenAPI接口定义/00-common.md §6`）。

**模型层 `RouteRulesManager.validateRouteRules`**（仅 Global 路由表的 manager 路径调用）为基础校验：规则名称必填且同组唯一、`Cond` 必填且为合法 BFE 条件表达式、`targets` 非空、每个 target 有 `Weight` 且权重和 =100、fallback `ClusterName` 非空。api-keys/entities 的模型层写路径直调 storager，不做校验——**对 OpenAPI 调用而言无缺口**，因为端点层已先行拦截。

> 注：两层规则集与错误消息存在差异（如单项权重范围、ClusterName 格式仅端点层校验），后续可考虑收敛为单一实现。

## 6. 三级路由表管理

### 6.1 Global 路由表

- 唯一记录：`type=global, owner=global`
- OpenAPI：
  - `GET /global-route-rules`
  - `PUT /global-route-rules`
- 系统初始化时，`stateful/container/rdb/components.go:Init()` 会调用 `RouteRulesManager.EnsureGlobalRouteRules` 自动创建一条默认记录（`enabled=false`、`rules=[]`），保证管理员首次进入路由管理列表页即可看到 Global 路由表。
- 若记录已存在（包括用户已更新过），不会覆盖现有数据。
- 不存在时 `PUT` 也会自动创建；存在时自动更新。
- 返回给前端时会隐藏内部 `id`。

### 6.2 Entity 路由表

Entity 路由表不通过独立端点管理，而是在 Entity 创建/更新时作为内嵌对象一起写入：

```go
// Entity 创建时的默认值
if param.RouteRules == nil {
    param.RouteRules = &shared.RouteRulesParam{
        Enabled: lib.PBool(false),
        Rules: []*shared.AiRouteRuleParam{},
    }
}
```

创建 Entity 时，其 `route_rules` 记录的 `type=entity, owner=<entity_id>`。

### 6.3 API-Key 路由表

与 Entity 类似，API-Key 路由表在 API-Key 创建/更新时作为内嵌对象写入：

```go
// API-Key 创建时的默认值
if param.RouteRules == nil {
    param.RouteRules = &shared.RouteRulesParam{
        Enabled: lib.PBool(false),
        Rules: []*shared.AiRouteRuleParam{},
    }
}
```

创建 API-Key 时，其 `route_rules` 记录的 `type=api_key, owner=<api_key_id>`。

### 6.4 路由表列表

`GET /route-tables` 用于分页列出所有路由表（仅返回 type/owner/enabled，不包含 rules 详情）：

```go
type RouteTableParam struct {
    Type string `json:"type"`
    Owner string `json:"owner"`
    Enabled bool `json:"enabled"`
}
```

## 7. 导出到 BFE

### 7.1 导出结构

AI 路由规则通过 `AIRouteExporter.ConfigExport` 导出为：

```go
type AiRouteDataExport struct {
    Version string `json:"Version"`
    RouteRules map[string]*RouteTableExport `json:"RouteRules"`
    ApikeyRouteTableBindings map[string][]string `json:"ApikeyRouteTableBindings"`
}
```

### 7.2 路由表命名

| 类型 | 导出 Key | Owner 字段 | `route_rules.type` 值 |
|------|---------|-----------|----------------------|
| API-Key | `apikey_<api_key_value>` | API-Key 的 key 值 | `apikey` |
| Entity | `entity_<entity_name>` | Entity 的 name | `entity` |
| Global | `global_default` | `global` | `global` |

> 注：`RouteRulesTypeAPIKey` 常量已由 `"api_key"` 修正为 `"apikey"`，与导出 Key 及 BFE 侧约定保持一致。历史 `type="api_key"` 记录建议迁移为 `"apikey"`。

### 7.3 绑定顺序

对每个 API-Key，绑定列表按以下顺序追加：

1. `apikey_<key>`（API-Key 级）
2. `entity_<entity_name>`（直接挂载 Entity）
3. `entity_<parent_name>` ……（沿 `parent_id` 向上遍历的所有祖先 Entity）
4. `global_default`（Global 级）

```go
for _, apiKey := range apiKeys {
    var bindingList []string

    // 1. API-Key level
    if apiKey.RouteRulesID != nil && enabled {
        bindingList = append(bindingList, fmt.Sprintf("apikey_%s", *apiKey.Key))
    }

    // 2. Entity level（自底向上遍历层级）
    currentEntityID := apiKey.EntityID
    for currentEntityID != nil && *currentEntityID != "" {
        entity, exists := entityMap[*currentEntityID]
        if !exists {
            break
        }
        if entity.RouteRulesID != nil && *entity.RouteRulesID != "" {
            bindingList = append(bindingList, fmt.Sprintf("entity_%s", *entity.Name))
        }
        currentEntityID = entity.ParentID
    }

    // 3. Global level
    if globalRouteRules != nil && enabled {
        bindingList = append(bindingList, "global_default")
    }

    bindings[*apiKey.Key] = bindingList
}
```

BFE 按列表顺序匹配，通常先命中 API-Key 级规则，再依次命中各级 Entity 规则，最后命中 Global 兜底规则。

### 7.4 导出到文件

通过 InnerAPI 导出时，生成 `ai_route.json`。

## 8. 与产品级路由规则的协同

完整请求链路：

```
Client
  → BFE 入口路由（Product Route Rules）
    → 命中 AI 网关 Cluster
      → BFE mod_api_key_rule 模块鉴权/配额/模型过滤
        → 命中 AI 路由表（ApikeyRouteTableBindings）
          → 按 Cond 匹配规则
            → 按 Weight 选择 Target Cluster + Model
              → 后端 AI 服务
```

- 产品级路由规则决定请求进入哪个 BFE Cluster；
- AI 路由规则在 API-Key 鉴权之后，决定请求最终转发到哪个后端模型与集群。

## 9. 与 API-Key / Entity 生命周期的一致性

### 9.1 创建 API-Key / Entity

创建时若传入了 `route_rules`，会同步创建 `route_rules` 记录，并把生成的 `id` 写回 `api_keys.route_rules_id` 或 `entities.route_rules_id`。

### 9.2 更新 API-Key / Entity

更新时若传入了 `route_rules`：

- 若已有 `route_rules_id`，则更新对应记录；
- 若没有，则创建新记录并写入 `route_rules_id`。

### 9.3 删除 API-Key / Entity

删除 API-Key / Entity 时，会级联删除其关联的 `route_rules` 记录：

```go
if one.RouteRulesID != nil {
    rppm.routeRulesStorager.DeleteRouteRules(ctx, *one.RouteRulesID)
}
```

### 9.4 切换 Entity

API-Key 从一个 Entity 切换到另一个 Entity 时：

- API-Key 自身的路由表 `route_rules_id` 不变；
- 导出时自动绑定新 Entity 的路由表。

## 10. 边界情况

| 场景 | 行为 |
|------|------|
| 路由规则 `enabled=false` | 不导出到 BFE，也不加入绑定列表 |
| API-Key 未挂载 Entity | 仅绑定自身路由表 + Global 路由表 |
| API-Key 与 Entity 都未配置路由表 | 仅绑定 Global 路由表（若 Global 启用） |
| Global 路由表禁用 | 无全局兜底，可能导致请求无规则可匹配 |
| Global 路由表记录被异常删除 | 系统重启后会自动重新创建默认记录；未重启时 `GET /global-route-rules` 返回 Data=null |
| 同一 Entity 名称变更 | 导出 Key `entity_<name>` 会变化，BFE 需重新加载 |
| `Cond` 表达式语法错误 | 当前保存阶段不校验，导出后可能导致 BFE 解析失败 |
| Target Weight 之和不等于 100 | 保存阶段直接报错 |
| 多个 target 指向同一 Cluster | 允许，权重合并由 BFE 处理 |
| AI 路由规则引用的 Cluster 被删除 | 删除集群时校验失败，返回引用冲突错误；需先解除引用或删除规则 |

## 11. 设计建议

1. **保存前校验 `Cond` 表达式**：建议复用 `RouteRuleManager.ExpressionVerify` 对每条 AI 路由规则的 `Cond` 做语法校验，避免下发到 BFE 后解析失败。
2. **条件表达式可视化**：Dashboard 可提供低代码方式生成 `Cond`，降低用户手写 BFE 表达式的门槛。
3. **Global 默认兜底**：强制要求至少配置一条 `default_t()` 或全匹配规则作为 Global 兜底，避免请求无目标。
4. **路由表版本号**：当前 AI 路由导出使用 `ZeroVersion`，建议与版本控制机制打通，支持增量同步。
5. **Entity 路由表独立端点**：当前 Entity 路由表只能通过 Entity 创建/更新内嵌维护，建议增加 `PUT /entities/{id}/route-rules` 独立端点，便于单独管理。
6. **路由规则调试工具**：提供模拟请求命中哪条规则的功能，方便排查路由问题。
7. **产品与 AI 路由解耦**：产品级路由规则与 AI 路由规则分别管理，文档与权限上需要明确区分，避免混淆。
