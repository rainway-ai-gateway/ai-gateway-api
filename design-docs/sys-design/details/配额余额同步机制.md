# 配额余额同步机制

## 1. 设计背景与目标

在 AI 网关的配额管理体系中，API-Key / Entity 的配额消耗发生在请求链路（由 BFE / 网关代理层实时扣减），而管理面（`ai-gateway-api`）需要向 OpenAPI 展示 `used` / `remaining`，并周期性（自然周 / 自然月）自动重置配额。

**核心矛盾**：请求链路扣减配额需要高并发、低延迟，因此使用 **Redis** 作为实时计数器；而管理面查询余额需要低延迟、高一致性的实时数据。

**解决思路**：采用 **“Redis 作为余额唯一真实来源”** 的架构：

- Redis 存储当前剩余配额（热数据），请求链路直接读写；
- OpenAPI 查询余额时直接读取 Redis，不再维护 `quota_balances` 冷数据副本；
- `last_reset_at` 保存在 `quota_plans` 表，周期重置逻辑只操作一张表；
- 手动重置 / 周期重置时，同步更新 Redis 与 `quota_plans.last_reset_at`；
- RMB 配额内部精度为 8 位小数（1e-8 元），对外统一按 4 位小数展示；Redis Lua 脚本使用整数运算避免浮点误差。

## 3. 核心数据结构

### 3.1 数据库表 `quota_plans`

```sql
CREATE TABLE `quota_plans` (
  `id` BIGINT NOT NULL AUTO_INCREMENT,
  `unlimited` TINYINT(1) DEFAULT 1,
  `pass_when_no_enough_quota` TINYINT(1) DEFAULT 0,
  `quota` DECIMAL(18,8) DEFAULT 0,
  `unit` VARCHAR(32) DEFAULT 'total_token',
  `reset_period` VARCHAR(16) DEFAULT 'never',
  `last_reset_at` DATETIME DEFAULT NULL COMMENT '上次重置时间',
  `created_at` DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  `updated_at` DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  INDEX `idx_unlimited` (`unlimited`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='配额计划表';
```

| 字段 | 类型 | 约束 | 说明 |
|------|------|------|------|
| `id` | BIGINT | 主键、自增 | 配额计划 ID |
| `unlimited` | TINYINT(1) | DEFAULT 1、索引 | 是否无限配额 |
| `pass_when_no_enough_quota` | TINYINT(1) | DEFAULT 0 | 配额不足时是否放行 |
| `quota` | DECIMAL(18,8) | DEFAULT 0 | 配额总量；`unit=total_token` 时存储为整数，`unit=RMB` 时最多保留 8 位小数 |
| `unit` | VARCHAR(32) | DEFAULT 'total_token' | 配额单位：`total_token`、`RMB` |
| `reset_period` | VARCHAR(16) | DEFAULT 'never' | 重置周期：`never` / `weekly` / `monthly` |
| `last_reset_at` | DATETIME | DEFAULT NULL | **上次重置时间**，周期重置据此判断是否跨越自然周/月边界 |
| `created_at` | DATETIME | NOT NULL | 创建时间 |
| `updated_at` | DATETIME | 自动更新 | 更新时间 |

### 3.2 Redis Key 规则

```go
// stateful/config_redis.go
func AIUsedQuotaKey(key string) string {
    return fmt.Sprintf("QUOTA_%s", key)
}
```

| 对象类型 | Redis Key 示例 | 说明 |
| --- | --- | --- |
| API-Key | `QUOTA_AI_product-abc123...` | 以 API-Key 的实际 `key` 值作为后缀 |
| Entity | `QUOTA_entity-1` | 以 `entity_id` 作为后缀 |
| 值语义 | 当前**剩余配额** | 网关层扣减时递减；`unit=total_token` 时值为整数，`unit=RMB` 时内部以 1e-8 元为单位的定点整数存储 |

> 注：与旧实现不同，当前 Redis Key **不再拼接 `KeyCreateAt` 时间戳**，生命周期与 API-Key / Entity 保持一致，避免 Key 膨胀。
>
> **RMB 配额精度说明**：
> - 内部精度：8 位小数（1e-8 元）定点数；
> - 外部展示：统一按 4 位小数输出；
> - Redis Lua 脚本使用整数运算避免浮点误差，即将 RMB 成本乘以 1e8 后转为整数进行扣减；
> - `unit = "total_token"` 仍直接使用整数计数；
> - `unit = "RMB"` 时，请求链路在扣减前需将实际成本转换为内部定点整数。

## 4. 配额缓存抽象（QuotaCache）

### 4.1 文件位置

- `model/quotacache/quotacache.go`
- `model/quotacache/redis.go`

### 4.2 接口定义

```go
type QuotaCache interface {
    // GetRemaining 获取指定对象的实时剩余配额（已按 unit 转换为浮点数）。
    GetRemaining(ctx context.Context, key string, unit *string) (float64, error)

    // BatchGetRemaining 批量获取指定对象的实时剩余配额。
    // keys 为 owner key（如 API-Key 的 key 或 entity_id），返回 map[ownerKey]remaining。
    BatchGetRemaining(ctx context.Context, keys []string, unit *string) (map[string]float64, error)

    // SetRemaining 将指定对象的 Redis 剩余量设置为 target。
    // 内部使用 IncrBy(delta) 保留当前 used，适用于 quota 调整场景。
    SetRemaining(ctx context.Context, key string, quota *float64, unit *string) error

    // ResetToQuota 将 Redis 剩余量重置为 quota 总量。
    // 内部复用 SetRemaining，使用 IncrBy(delta)。
    ResetToQuota(ctx context.Context, key string, quota *float64, unit *string) error

    // ResetToQuotaAtomic 将 Redis 剩余量原子地覆盖为 quota 总量。
    // 内部使用 Lua + SET，不依赖当前值，专用于周期重置，避免并发读-算-写 race。
    ResetToQuotaAtomic(ctx context.Context, key string, quota *float64, unit *string) error

    // DeleteKeys 删除指定对象的 Redis 配额 Key。
    DeleteKeys(ctx context.Context, keys []string) error
}
```

### 4.3 Redis 实现

`RedisQuotaCache` 封装对 `bfe_util/redis_client.Client` 的调用：

- `GetRemaining`：读取单个 `QUOTA_<key>`，将定点整数转换为浮点数；Key 不存在时返回 0。
- `BatchGetRemaining`：调用 `client.GetInt64Batch(keys)` 批量读取，减少网络往返；返回 `map[ownerKey]remaining`。
- `SetRemaining`：先读取当前值，计算 `delta = target - current`，通过 `IncrBy(delta)` 原子调整；Key 不存在时 `current = 0`。适用于 `ApplyQuotaPlanChange` 等需要保留 `used` 的场景。
- `ResetToQuota`：与 `SetRemaining` 共用实现，通过 `IncrBy(delta)` 将剩余量调整为 `quota`。
- `ResetToQuotaAtomic`：通过 Lua 脚本直接 `SET` Redis Key 为 quota 总量，不读取当前值，消除单条写操作内部的 read-modify-write race；专用于周期重置。
- `DeleteKeys`：删除 `QUOTA_<key>`，用于 API-Key / Entity 删除后的清理。

### 4.4 Redis 客户端批量接口

`bfe/bfe_util/redis_client/client.go` 扩展了批量读取能力：

```go
type Client interface {
    // ... 原有方法
    GetInt64Batch(keys []string) ([]int64, error)
}
```

实现按 Redis 集群 ID 对 keys 分组，对每个集群执行 `MGET`，合并结果后返回。

## 5. 调度器（QuotaResetScheduler）

### 5.1 调度策略

当前实现采用**单一高频调度器**，每分钟执行一次；多实例部署时通过 **Redis 分布式锁**保证同一时刻只有一个实例执行重置任务：

```go
func (s *QuotaResetScheduler) run() {
    s.resetQuotasWithRecover()

    ticker := time.NewTicker(1 * time.Minute)
    defer ticker.Stop()

    for {
        select {
        case <-ticker.C:
            s.resetQuotasWithRecover()
        case <-s.stopCh:
            return
        }
    }
}
```

每次调度**仅执行** `ResetExpiredBalances()`，不再执行 `SyncAllBalances()`。

```go
func (s *QuotaResetScheduler) resetQuotas() {
    ctx := context.Background()
    now := time.Now()

    stateful.AccessLogger.Info("Starting quota scheduler tasks at %v", now)

    if s.lockClient != nil {
        lockKey := "quota:reset:scheduler:lock"
        ttl := 5 * time.Minute

        acquired, err := s.lockClient.Acquire(ctx, lockKey, s.instanceToken, ttl)
        if err != nil || !acquired {
            stateful.AccessLogger.Info("Quota scheduler lock not acquired, skip")
            return
        }

        stopRenew := s.startRenew(ctx, lockKey, ttl)
        defer stopRenew()
        defer s.lockClient.Release(ctx, lockKey, s.instanceToken)
    }

    if err := s.balanceSyncMgr.ResetExpiredBalances(ctx); err != nil {
        stateful.AccessLogger.Error("Failed to reset expired balances: %v", err)
    }
}
```

> 说明：旧实现会先执行 `SyncAllBalances()` 再执行 `ResetExpiredBalances()`。重构后 `quota_balances` 表已删除，`SyncAllBalances()` 同步逻辑不再存在。

分布式锁特性：

- 锁 key：`quota:reset:scheduler:lock`；
- 锁 value：实例唯一 token（`uuid`），释放/续期时校验 token，防止误删他人锁；
- TTL：5 分钟，任务执行期间通过看门狗每 `TTL/3` 续期一次；
- 锁实现位于 `model/quotacache/lock.go`，基于 Redis Lua 脚本完成 `Acquire` / `Release` / `Renew`。

为便于测试与运维排障，提供手动触发接口：

- `POST /inner-api/v1/quota/trigger-reset`：立即触发一次带锁保护的周期重置任务，不影响调度器下次执行时间。

### 5.2 可测试性设计

为了让时间相关的周期重置逻辑可测试，`model/quota` 引入了 `Clock` 接口：

```go
// Clock 提供当前时间。
type Clock interface {
    Now() time.Time
}
```

`BalanceSyncManager` 构造时注入 `Clock`，`nil` 时默认使用 `NewRealClock()`：`ResetExpiredBalances` 内部通过 `m.clock.Now()` 获取当前时间，从而判断自然周/月边界。

### 5.4 多实例部署说明

当前 `QuotaResetScheduler` 在每个 `ai-gateway-api` 实例中独立启动。多实例部署时，通过 Redis 分布式锁保证**同一时刻只有一个实例**执行 `ResetExpiredBalances()`：

- 各实例竞争全局锁 `quota:reset:scheduler:lock`；
- 获取锁的实例在 5 分钟 TTL 内执行全部重置任务，看门狗自动续期；
- 未获取锁的实例直接跳过本次调度；
- 持有锁的实例崩溃后，锁会在 TTL 到期后自动释放，其他实例可继续替补。

> 注意：分布式锁能避免多实例并发遍历和写 Redis / DB，但无法完全消除崩溃窗口。采用"先认领（条件更新 `last_reset_at`）后 SET Redis"的顺序后，残留窗口变为"实例 A 已认领、尚未 SET Redis 即崩溃"——此时本周期不再补重置（`SET` 幂等，下一周期正常推进），相比旧顺序"重复 SET 抹掉合法消耗"是更安全的失败方向。该窗口在 10. 边界情况中说明。

### 5.5 测试方法

## 6. 配额重置机制

### 6.1 周期重置 `ResetExpiredBalances`

支持两种重置周期：

- `weekly`：自然周，每周一 00:00:00 重置；
- `monthly`：自然月，每月 1 日 00:00:00 重置。

`ResetExpiredBalances` 通过注入的 `Clock` 获取当前时间，再调用 `shouldResetByPeriod` 判断是否跨越周期边界：

```go
now := m.clock.Now()
```

判断逻辑：

```go
func (m *BalanceSyncManager) shouldResetByPeriod(
    lastResetAt *time.Time,
    resetPeriod string,
    now time.Time,
) bool {
    if lastResetAt == nil {
        return true
    }

    switch resetPeriod {
    case "weekly":
        return getWeekStart(now).After(getWeekStart(*lastResetAt))
    case "monthly":
        return getMonthStart(now).After(getMonthStart(*lastResetAt))
    }
    return false
}
```

`getWeekStart` / `getMonthStart` 将时间归一化为周一或每月 1 日的 00:00:00（本地时区）。

### 6.2 重置执行流程

1. 查询 `reset_period` 为 `weekly` 或 `monthly` 且非无限配额的计划；
2. 判断是否需要重置；
3. **先认领**：条件更新 `quota_plans.last_reset_at = now()`，仅当 `last_reset_at IS NULL`（从未重置）**或** `last_reset_at < 周期开始时间` 时才更新；`affected = 0` 表示本周期已被认领，直接跳过；
4. 认领成功（`affected > 0`）后，对计划下所有 API-Key / Entity 的 Redis Key 执行**原子 `SET`**，将剩余量覆盖为配额总量。

> 认领必须先于 Redis 重置（issue #228）：条件更新本身就是"本轮归我重置"的认领标志，放在 Redis 写入之前，多实例 / 锁失效窗口下同周期全局至多被一个实例重置一次；若放在重置之后，竞争失败的实例也已经完成了 Redis 覆盖。

```go
func (m *BalanceSyncManager) ResetExpiredBalances(ctx context.Context) error {
    return m.txn.AtomExecute(ctx, func(ctx context.Context) error {
        plans, err := m.planStorager.FetchQuotaPlanList(ctx, &QuotaPlanFilter{
            ResetPeriod: []string{"weekly", "monthly"},
            Unlimited: lib.PBool(false),
        })
        // ...

        now := m.clock.Now()
        for _, plan := range plans {
            if !m.shouldResetByPeriod(plan.LastResetAt, *plan.ResetPeriod, now) {
                continue
            }

            // 1. 先认领：条件更新 last_reset_at（NULL 或早于周期开始时间才命中）
            periodStart := m.getPeriodStart(*plan.ResetPeriod, now)
            affected, err := m.planStorager.ClaimQuotaPlanReset(ctx, *plan.ID, periodStart, now)
            if err != nil {
                continue // 认领失败，下一周期重试
            }
            if affected == 0 {
                continue // 本周期已被认领（多实例竞争）
            }

            // 2. 认领成功后原子 SET Redis
            if err := m.resetAPIKeysRedisUsage(ctx, *plan.ID); err != nil {
                continue // last_reset_at 已推进，本轮不补重置（SET 满额幂等）
            }
        }
        return nil
    })
}
```

条件更新（认领）对应的 SQL：

```sql
UPDATE quota_plans
SET last_reset_at = ?
WHERE id = ?
  AND (last_reset_at IS NULL OR last_reset_at < ?)
```

其中第一个 `?` 为本次重置时间，第三个 `?` 为当前周期的开始时间。该语句通过 `ClaimQuotaPlanReset` 专用 DAO 方法执行（gendry where map 不支持 `IS NULL OR <` 组合，且三值逻辑下 `last_reset_at < ?` 对 NULL 行恒不成立——历史上实现误用 `<` 条件导致 NULL 计划标记永不落库、每分钟重复重置）。该条件作为分布式锁之外的第二道幂等防线：即使锁异常失效导致两个实例先后执行，第二个实例也会因 `last_reset_at >= 周期开始时间` 而更新 0 行，避免重复重置。

此外，计划在创建时即初始化 `last_reset_at`：`reset_period` 为 `weekly`/`monthly` 的计划在创建路径中将 `last_reset_at` 置为创建时间（存储层 `QuotaPlanStorager.CreateQuotaPlan` 统一处理，含 API-Key / Entity 嵌套创建），从源头避免 NULL 进入调度判定；存量 NULL 行由修复后的首次调度自然回填。

### 6.3 Redis 归零策略

不同场景使用不同的 Redis 写入方式：

| 场景 | 调用方法 | Redis 操作 | 说明 |
|------|---------|-----------|------|
| 手动重置 / 配额计划变更 | `ResetToQuota` / `SetRemaining` | `GetInt64 + IncrBy(delta)` | 保留 `used`，仅调整剩余量；与其他扣减操作串行化 |
| 周期重置（定时调度器） | `ResetToQuotaAtomic` | Lua + `SET` | 不依赖当前值，原子覆盖为 quota 总量，避免并发读-算-写 race |

周期重置使用 `SET` 的原因：

- 周期重置的语义是“把剩余量恢复为 quota 总量”，不需要保留当前值；
- `SET` 是原子操作，不存在 `GetInt64 + IncrBy(delta)` 内部“读-算-写”的 race；
- 多实例部署下，即使锁正常持有，仍可能因崩溃恢复导致不同实例先后进入重置流程；`SET` 保证单条 Redis 写操作本身是幂等的。

> 注意：`ResetToQuotaAtomic` 仅用于 `BalanceSyncManager.resetAPIKeysRedisUsage`，`ApplyQuotaPlanChange` 等差额调整场景继续调用 `SetRemaining`，以保留 `used`。

### 6.4 手动重置接口

提供两个 OpenAPI 端点，均调用 `QuotaPlanManager.ResetBalance(..., updateLastResetAt=false)`：

- `POST /api-keys/{id}/quota-plan/reset`
- `POST /entities/{id}/quota-plan/reset`

`updateLastResetAt=false` 的设计意图：手动重置不应干扰周期调度器对自然周 / 自然月的判断。

`QuotaPlanManager.ResetBalance` 核心逻辑：

```go
func (m *QuotaPlanManager) ResetBalance(
    ctx context.Context,
    planID int64,
    newQuota *float64,
    updateLastResetAt bool,
) error {
    return m.txn.AtomExecute(ctx, func(ctx context.Context) error {
        // 1. 校验 plan 存在且非无限
        // 2. 若 newQuota 不为空，更新 plan.quota
        // 3. 重置 Redis 余额
        // 4. 按需更新 quota_plans.last_reset_at
    })
}
```

**错误语义**（issue #183）：手动重置为管理写入，失败遵循 2xx/4xx/422 语义。目标计划 `unlimited=true` 时返回 422 `Param Illegal: cannot reset balance for unlimited quota`（模型层以 `xerror.WrapParamErrorWithMsg` 定型为 PARAM 类型，禁止裸 error 被兜底为 500 Unknown Exception），不产生配额变更，并在事务返回后记录 `quota_plan/reset`、`status=2`、error_msg 非空、`resource_parent_id` 为 owner 业务 ID 的操作日志（SC2101-TC047 断言 3）。

## 7. Redis Key 生命周期

| 阶段 | 行为 | 说明 |
| --- | --- | --- |
| **API-Key / Entity 创建** | 若配额有限，调用 `quotacache.SetRemaining` 将 Redis 值设为 `quota` | 由 `model/api_key.APIKeyManager.CreateAPIKey` / `model/entity.EntityManager.CreateEntity` 在事务提交后调用；`unit=RMB` 时 Redis 存定点整数 |
| **Entity 无限配额** | 设置默认大值 `100000000` | 保证无限配额对象在 Redis 中也有可读取的剩余量 |
| **请求链路消耗** | 网关层对 `QUOTA_<key>` 做递减 | 不在 `ai-gateway-api` 内实现；`unit=RMB` 时 Lua 使用整数运算 |
| **手动重置** | `IncrBy(delta)` 调整为新的 `quota` | 不删除/新建 Key；`unit=RMB` 时按定点整数计算 delta |
| **周期重置** | Lua + `SET` 覆盖为 `plan.Quota` | 同时条件更新 `quota_plans.last_reset_at`；`unit=RMB` 时按定点整数计算；多实例由分布式锁保护 |
| **API-Key / Entity 删除** | 事务提交后调用 `quotacache.DeleteKeys` 删除 `QUOTA_<key>` | 控制面主动清理，避免内存泄漏和 Key 复用 |

> 说明：旧实现中存在“定时同步任务读取 Redis 回写 `quota_balances`”阶段，已随 `quota_balances` 表一起移除。

## 8. 查询时的余额获取

OpenAPI 查询 API-Key / Entity 详情或列表时，余额由 Manager 层的 `populateQuotaBalance` / `populateQuotaBalances` 自动填充，无需端点层额外处理。

### 8.1 直接读取 Redis

`model/api_key/api_key.go` 与 `model/entity/entity_manager.go` 查询路径：

1. 读取 `api_keys` / `entities` 与关联的 `quota_plans`；
2. 对非无限配额对象，通过 `quotaCache.GetRemaining`（单对象）或 `quotaCache.BatchGetRemaining`（列表）读取 Redis 剩余量；
3. 根据 `used = quota - remaining` 计算已用量，填充 `QuotaPlan.Balance`。**不对负 remaining 钳零**（issue #1476）：BFE 全额扣减后余额可为负，`used` 如实反映实际消耗、允许大于 `quota`（超出部分即超额用量），`Balance.Remaining` 展示值钳 0；
4. 无限配额对象填充 sentinel balance（`used=0`，`remaining=100000000`）。

列表接口批量读取逻辑：

```text
for each item in list:
    if unlimited: fill sentinel balance
    else: collect owner key -> item mapping, grouped by unit

for each unit group:
    result = quotaCache.BatchGetRemaining(keys, unit)
    for each item: fillQuotaBalance(item.one.QuotaPlan, result[item.key])
```

### 8.2 余额字段语义

`QuotaPlanParam.Balance`（`shared.QuotaBalanceParam`）字段语义不变：

- `used`：已使用量；**允许大于 `quota`**（issue #1476 起，超额部分 = 欠费量 = `used − quota`）；
- `remaining`：剩余量；Redis 余额为负（欠费）时对外展示为 0；
- 无限配额返回 `used=0`、`remaining=100000000`；
- `unit=RMB` 时对外统一按 4 位小数展示。

> `GET /api-keys` 与 `GET /api-keys/{id}` 的返回中，`quota_plan` 均已包含 `balance`。该余额来自**Redis**，是实时数据。Redis 不可用时，查询接口会报错；不再降级到数据库 `quota_balances`。

### 8.3 实时剩余量查询 `GetRemainingQuota`

`model/api_key/api_key.go` 提供了实时读取 Redis 的辅助函数，供网关层或内部逻辑使用：

```go
func GetRemainingQuota(ctx context.Context, param *APIKeyParam) (*float64, error) {
    if param.UnlimitedQuota != nil && *param.UnlimitedQuota {
        return nil, nil
    }

    // 关联的 quota plan 为无限配额时，同样返回 nil
    if param.QuotaPlan != nil && param.QuotaPlan.Unlimited != nil && *param.QuotaPlan.Unlimited {
        return nil, nil
    }

    if param.QuotaPlan == nil || param.QuotaPlan.Quota == nil {
        return nil, nil
    }
    if quotaCache == nil {
        return param.QuotaPlan.Quota, nil
    }

    remain, err := quotaCache.GetRemaining(ctx, *param.Key, param.QuotaPlan.Unit)
    if err != nil {
        return nil, err
    }
    if remain < 0 {
        remain = 0
    }
    return &remain, nil
}
```

**语义**：

- API-Key 自身或关联 quota plan 为无限配额：返回 `nil`，表示无限制；
- 有限配额且 Redis Key 不存在：返回 `plan.Quota`（未使用）；
- 有限配额且 Redis Key 存在：返回 Redis 当前值；`unit=RMB` 时 Redis 值为定点整数，需除以 1e8 转换为浮点数；
- 值为负时截断为 0。

## 9. 创建与删除时的一致性处理

### 9.1 创建时初始化

- API-Key / Entity 创建若携带**有限配额计划**，`model/api_key.APIKeyManager.CreateAPIKey` / `model/entity.EntityManager.CreateEntity` 会在事务提交后通过 `quotacache.QuotaCache.SetRemaining` 向 Redis 写入初始剩余量；
- 数据库中不再创建 `quota_balances` 记录；
- 若 Redis 写入失败，接口可能返回错误，但数据库记录已存在；管理员可后续通过手动重置接口修复。

### 9.2 更新配额计划时的余额处理

无论是 `PUT` 全量更新还是 `PATCH` 部分更新，Manager 层（`APIKeyManager.UpdateAPIKey` / `EntityManager.UpdateEntity`）仅负责完成数据库内 `api_keys` / `entities` 及 `quota_plans` 的持久化，**不再在事务提交后无条件同步 Redis**。配额余额的调整由 Endpoint 层根据新旧 `quota_plan` 的差异，调用 `QuotaPlanManager.ApplyQuotaPlanChange` 完成。

调用位置：

- `endpoints/openapi_v1/api_key/update.go`
- `endpoints/openapi_v1/api_key/full_update.go`
- `endpoints/openapi_v1/entity/update.go`
- `endpoints/openapi_v1/entity/full_update.go`

示例逻辑（以 API-Key 部分更新为例）：

```go
if param.QuotaPlan != nil && updated != nil && updated.QuotaPlanID != nil {
    if err := container.QuotaPlanManager.ApplyQuotaPlanChange(
        ctx, *updated.QuotaPlanID, existing.QuotaPlan, param.QuotaPlan,
    ); err != nil {
        return nil, err
    }
}
```

`QuotaPlanManager.ApplyQuotaPlanChange` 的行为：

1. 比较旧 `quota_plan` 与新 `quota_plan` 的 `quota`、`unit`、`unlimited`；
2. 若三者均未变化（例如仅修改 `pass_when_no_enough_quota`、`reset_period` 或 API-Key 其他属性）：直接返回，不调整 balance 与 Redis；
3. 若 `quota` 变化且 `unit` 不变：保留 `balance.used`，按 `remaining = 新quota - used` 更新 balance，并通过 `QuotaCache.SetRemaining` 原子调整 Redis（内部使用 `IncrBy(delta)`）。**结果不再钳零**（issue #1476）：`used` 可大于旧 `quota`（欠费状态），此时 `remaining` 可为负——负值表示新配额仍不足以覆盖已用量，BFE 鉴权继续拒绝；
4. 若 `unit` 发生变化（如 `total_token` ↔ `RMB`）：由于新旧单位无法直接换算，重置 `balance.used = 0`、`balance.remaining = 新quota`，并通过 `QuotaCache.ResetToQuota` 重置 Redis；
5. 若 `unlimited` 由 `false` 改为 `true`：将 balance 置为无限制状态（`used = 0`，`remaining = sentinel`），Redis 同步为 sentinel；
6. 若 `unlimited` 由 `true` 改为 `false`：创建/更新 balance（`used = 0`，`remaining = quota`），Redis 同步为 quota。

> 注：端点层不再直接调用 Redis Client；`ApplyQuotaPlanChange` 负责 Redis 的最终一致。

**关键变化**：

- 修改 `quota_plan.quota` 不再清零 `used`，而是保留历史使用量；
- 修改 `quota_plan.unit` 或 `unlimited` 才会重置 `used`；
- 修改 `quota_plan` 的其他字段或 API-Key / Entity 普通属性不会影响配额余额。

### 9.3 删除时清理

- `APIKeyManager.DeleteAPIKey` / `EntityManager.DeleteEntity` 在事务内级联删除 `quota_plan` 等关联记录；
- 事务提交后，调用 `quotacache.QuotaCache.DeleteKeys` 主动删除对应的 `QUOTA_<key>`；
- 删除只针对被删除的 API-Key / Entity 自身，不清理所属 Entity 或父 Entity 的 Quota Key。

## 10. 边界情况与注意事项

| 场景 | 当前行为 | 说明 |
| --- | --- | --- |
| Redis Key 不存在 | `remaining = quota`、`used = 0` | 新创建对象或 Redis 数据被清理后首次查询时适用 |
| Redis 值为负 | `remaining` 置 0 | 防止透支导致展示异常 |
| RMB 配额小数位超过 8 位 | 接口层校验拒绝或截断 | 内部定点精度为 1e-8 元；对外统一按 4 位小数展示 |
| 无限配额计划 | 返回 sentinel balance；不参与周期重置 | `Unlimited=true` 时 Redis 也写入 sentinel，网关层按无限配额处理 |
| 仅修改 `quota`（单位不变） | 保留 `balance.used`，`remaining = max(0, 新 quota - used)`，Redis 按 delta 原子调整 | 通过 `QuotaPlanManager.ApplyQuotaPlanChange` 实现，避免普通调额清空历史用量 |
| 修改 `unit` | `used` 与 `remaining` 均重置，`remaining = 新 quota`；Redis 覆盖为新值 | 新旧单位无法直接换算，按全新配额处理 |
| `unlimited` 由 `false` 改为 `true` | `used = 0`，`remaining = sentinel`，Redis 同步为 sentinel | sentinel 值为 `100000000`，网关层按无限配额处理 |
| `unlimited` 由 `true` 改为 `false` | `used = 0`，`remaining = quota`；Redis 同步为 quota | 与单位变化同样按全新配额处理 |
| 仅修改 quota_plan 其他属性（如 `reset_period`、`pass_when_no_enough_quota`）或 API-Key / Entity 普通属性 | 不调整 balance 与 Redis | `ApplyQuotaPlanChange` 仅在 `quota`/`unit`/`unlimited` 变化时生效 |
| Redis 读取失败 | OpenAPI 查询接口报错 | 删除 `quota_balances` 兜底后，Redis 异常直接影响管理面查询；需监控 Redis 可用性 |
| 多实例部署 | 各实例均会启动调度器，通过 Redis 分布式锁互斥 | 同一时刻仅一个实例执行；锁 TTL 5 分钟 + 看门狗续期，崩溃后可故障转移 |
| 实例崩溃在认领 DB 与 SET Redis 之间 | 极端小概率窗口 | 实例 A 条件认领（`last_reset_at` 已推进）后、SET Redis 前崩溃；实例 B 获得锁后因 `last_reset_at >= 周期开始时间` 认领 0 行而跳过，本周期不再重置。相比旧顺序（先 SET 后更新 DB，B 会重复 SET、可能抹掉合法消耗）失败方向更安全；如业务要求"周期必重置"，可引入 Redis marker + Lua 原子检查 |
| 时区 | 使用服务器本地时区 | `getWeekStart` / `getMonthStart` 依赖 `time.Now()` 的本地时区 |
| 单条失败 | 记录日志并继续 | 不影响其他计划 / 对象的处理 |

## 11. 数据迁移

上线前需一次性将 `quota_balances.last_reset_at` 回写到 `quota_plans.last_reset_at`：

```sql
UPDATE quota_plans qp
JOIN quota_balances qb ON qp.id = qb.quota_plan_id
SET qp.last_reset_at = qb.last_reset_at;
```

SQLite 使用对应 UPDATE 语法。

迁移完成后，确认 `quota_balances` 表无其他系统依赖，即可删除该表。
