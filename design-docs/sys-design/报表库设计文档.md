# Rainway AI Gateway - 报表库设计文档

> 本文档描述**报表库**（如 `bfe_report`）的表结构设计。报表库与控制面库（见 [数据库设计文档.md](./数据库设计文档.md)，34 张控制面表）**分离部署、独立授权**，由 log-reader `mod_log_mysql` 插件写入、报表查询 API（`/report/*`，见 [details/报表查询模块.md](./details/报表查询模块.md)）读取。模块接口定义见 [api-define/OpenAPI接口定义/report.md](../api-define/OpenAPI接口定义/report.md)。ai-cache / 流量镜像 / ai-intent 三组访问日志新字段的加列见 [modifications/2026-09-27-report-cache-mirror-intent-fields](../modifications/2026-09-27-report-cache-mirror-intent-fields/design-changes.md)。

## 1. 概述

| 项目 | 说明 |
|------|------|
| 库定位 | AI 访问日志的报表存储库，独立于 ai-gateway-api 控制面库 |
| 数据生产者 | log-reader `mod_log_mysql` 插件（批量幂等写入明细表）；ai-gateway-api 分钟聚合 JOB（明细 → 聚合表） |
| 数据消费者 | ai-gateway-api 报表查询 API（时序/排行/分布读聚合表，明细查询读明细表） |
| 部署形态 | 轻量形态用 MySQL 8.0（推荐）/5.7.8+；标准形态用 Doris，表结构权威在 `ai-gateway-observability/doris/sqls/`，本文档 §3/§4 的列设计与其对齐 |
| DDL 维护 | 统一在本仓库 `db_ddl_report_mysql.sql`，随本仓库发布，部署流程执行（schema-first：先 DDL 后启用插件）；写入插件不自动建表 |

### 1.1 表清单

| 表名 | 作用 | 数据来源 | 读取方 |
|------|------|----------|--------|
| `bfe_ai_request_log` | 明细表，AI 请求日志宽表（101 列 = 99 列 + issue #1479 缺价信号 2 列，与 Doris 明细表同名同列） | log-reader 插件 `INSERT ... ON DUPLICATE KEY UPDATE` 幂等覆盖写 | `/report/logs` 明细分页；overview 缓存/镜像/意图明细 count |
| `bfe_ai_metrics_1m` | 分钟聚合表（40 维 + 24 指标，与 Doris 同名表维度集合对齐；`ai_cache_status` / `mirror_hit` / `ai_intent_answer` 三个维度列一期仅 MySQL 侧） | api-gateway-api 聚合 JOB（`DELETE` 窗口 + `INSERT SELECT` 事务，窗口重放幂等） | `/report/overview` / `timeseries` / `rankings` / `distribution` |

数据流：`bfe_ai_request_log`（明细）→ 聚合 JOB 按「上一整分钟」窗口汇总 → `bfe_ai_metrics_1m`（聚合）。时序/排行/分布类查询**只读聚合表**，不扫明细大表。

## 2. 通用约定

- 引擎 InnoDB，字符集 `utf8mb4`；要求 MySQL ≥ 5.7.8（JSON 列），推荐 8.0。
- 两表均按时间列（`log_time` / `ts_min`）**按天 RANGE 分区**；MySQL 无动态分区，分区由 api-gateway-api 分区管理 JOB 维护（提前建 3 天、DROP 超 `RetentionDays` 的分区；非分区形态自动降级 `DELETE ... LIMIT` 分批）。
- **NULL 语义**：写入侧（log-reader）零值规则为「字符串空值 → NULL，数值/布尔零值 → 0」；查询侧过滤空值统一 `IFNULL(col,'') != ''`；聚合 JOB 写入聚合表时维度列 `IFNULL(col,'')` 归一（与 Doris 聚合 JOB 的 COALESCE 语义一致）。
- JSON 列只用于明细页展示，不做查询过滤条件（避免生成列/函数索引的兼容性问题）。

## 3. 明细表 `bfe_ai_request_log`

与 Doris 明细表同名同列；差异仅在类型适配：Doris 的 `ARRAY<STRUCT<...>>` 列用 `JSON` 存储（7 个：`req_headers`、`res_headers`、`ai_route_rule_hits`、`ai_cluster_key_names`、`ai_rate_limit_hits`、`ai_auth_reject_quota_plans`、`ai_auth_hit_quota_plans`），`log_time` 用 `DATETIME`。

AI 可观测列段末尾的 10 个缓存/镜像/意图列（2026-09-27 变更，proto v0.3.7/3.8/3.9 字段，列序与 log-reader `mod_log_mysql/field_mapper.go` 扩列后的列序一致）：

| 列 | 类型 | 说明 |
|----|------|------|
| `ai_cache_status` | VARCHAR(16) NOT NULL DEFAULT '' | 缓存命中状态：hit/miss/skip；空=未启用缓存 |
| `mirror_hit` | TINYINT NOT NULL DEFAULT 0 | 是否被流量镜像 |
| `mirror_cluster` | VARCHAR(128) NOT NULL DEFAULT '' | 镜像目标集群名 |
| `ai_intent_question` | VARCHAR(64) NOT NULL DEFAULT '' | 路由实际消费的问题名 |
| `ai_intent_answer` | VARCHAR(64) NOT NULL DEFAULT '' | 分类答案，含 unknown |
| `ai_intent_confidence` | DOUBLE DEFAULT NULL | 门控后置信度 |
| `ai_intent_source` | VARCHAR(32) NOT NULL DEFAULT '' | explicit_header/classifier/cache |
| `ai_intent_latency_us` | BIGINT DEFAULT NULL | 决策耗时（μs） |
| `ai_intent_cache_hit` | TINYINT DEFAULT NULL | 意图 LRU 缓存命中 |
| `ai_intent_questions_version` | VARCHAR(32) NOT NULL DEFAULT '' | questions 配置版本 |

### 3.2 设计要点（经 log-reader LR03 集成测试在真实 MySQL 8.4 上验证）

1. **长文本列用 TEXT**：`origin_uri`/`final_uri`/`x_forward_for`/`authorization`/`referrer`/`user_agent`/`cookie`/`res_location` 若按 Doris 的 VARCHAR 长度建列，utf8mb4 下总长度超过 MySQL 65535 字节行上限（Error 1118）。
2. **幂等键中的字符串列允许 NULL**：`ai_apikey_id`/`ai_requested_model` 为 `DEFAULT NULL`——写入侧零值规则把空字符串映射为 NULL（未认证请求即如此），`NOT NULL` 会使这类写入整批失败（Error 1048）。副作用：NULL 不参与唯一键去重（与 Doris UNIQUE KEY 对 NULL 的语义一致），无 Key 日志重发不去重，可接受。`hostid`/`log_time` 由 log-reader 构造保证非空，保持 `NOT NULL`。
   - **`logid` 是例外，必须 `NOT NULL DEFAULT 0`**（issue #1417）：MySQL 唯一键视 NULL 互不相等，若 `logid` 可空，缺 id 的行会**逃出全部去重**——同一行重放插入重复行，把"覆盖丢行"换成"重放重复行"；`DEFAULT 0` 使无 id 的行仍参与比较，与旧的四元组覆盖行为**逐行等价**。写入侧对 `logid` 恒写整数（pb 字段为 `uint64`，不写 NULL），该约束是防御性的。
3. **唯一键 = 请求级判别键**（issue #1417 起）：`(hostid, log_time, ai_apikey_id, ai_requested_model, logid)` + `ON DUPLICATE KEY UPDATE` 覆盖写。`logid` 入键前，键退化为"秒 + Key + 模型"，同秒同 Key 同模型的并发请求互相覆盖（生产实测丢率恰为 (n−1)/n、窗口 13.5%）；入键后并发请求各自成行，只有**同一请求重放**（同 `logid`）才命中覆盖，重发、重启 `-b` 补读仍不产生重复行。键长 `(256+256+128)*4 + 长度字节 + 5(log_time) + 8(BIGINT) ≈ 2579` 字节 < 3072 InnoDB 上限（DYNAMIC 行格式），无需前缀索引；唯一键仍含分区列 `log_time`，满足"分区表唯一键必须包含全部分区列"，**因此分区管理与保留期行为不变**。
   - **与 Doris 的一致性：列契约一致，唯一键语义待同改**。Doris 明细表（`ai-gateway-observability/doris/sqls/bfe_ai_request_log.sql`）仍是原四元组 `UNIQUE KEY`，同缺陷未修；本仓侧不再宣称"与 Doris UNIQUE KEY 完全一致"。DDL、迁移 runbook 与两端差异见变更记录 `design-docs/modifications/2026-10-13-issue-1417-report-detail-dedup-key-logid/`。
4. **索引服务于报表查询过滤维度**：模型/API Key/提供商/Host/状态码 + 时间，与 `/report/*` 过滤参数对应。
5. **pb 中已有、本表不含的新字段**（如 `ai_image_input_tokens`、`ai_video_count`）：待 Doris 侧表升级时两侧同步加列（见 §6 演进规则）。

### 3.3 明细表生命周期

按天分区滚动：分区管理 JOB 每 6h 巡检，向前建 3 天分区、`DROP PARTITION` 清理超过 `RetentionDays`（默认 7 天）的历史分区（DROP PARTITION 秒级、无碎片）。**JOB 必须先于数据到达建好分区**，否则对应日期的写入被直接拒绝（Error 1526）；JOB 启动时立即补建一次。

## 4. 聚合表 `bfe_ai_metrics_1m`

维度集合与指标列与 Doris `bfe_ai_metrics_1m` 对齐（Doris DDL 见 `ai-gateway-observability/doris/sqls/bfe_ai_metrics_1m.sql`）：40 个维度列（`ts_min` 分钟桶 + 16 个基础维度 + 10 个标签打平列 + 限流三元组 + 认证拒绝原因 + 5 个配额计划槽位 + 3 个缓存/镜像/意图维度）+ 24 个 SUM 指标列（请求数、错误数、认证拒绝数、进出/总/缓存/音频/图片 Token、TTFT/TPOT 累计、请求响应字节、限流命中、后端重试、耗时累计、成本累计）。

2026-09-27 变更新增 3 个维度列（普通 ALTER；低基数：ai_cache_status ≤4 值、mirror_hit 2 值、ai_intent_answer ≤问题选项数）：

| 新维度列 | 来源（明细列） | 维度常量（model/ireport） |
|----------|----------------|---------------------------|
| `ai_cache_status` | `ai_cache_status`（IFNULL 归一） | `DimensionCacheStatus` |
| `mirror_hit` | `mirror_hit`（0/1） | `DimensionMirrorHit` |
| `ai_intent_answer` | `ai_intent_answer`（IFNULL 归一；`ai_intent_question` 不进聚合——一期 BFE 只记路由消费的单条，question 恒为被消费的那个） | `DimensionIntentAnswer` |

行数膨胀评估：3 个维度基数低，分钟 × 既有维度组合膨胀估 10–30 倍于相关子集，分钟表仅近期窗口，可接受；上线后监控 JOB 耗时与表行数，超预期时降级预案为 intent 维度降采样或缩短分钟表保留期。

### 4.2 设计要点

1. **不设唯一键/主键**：40 个维度列（含多个 VARCHAR(256)）无法构成 InnoDB 唯一键（3072 字节上限），且幂等性由聚合 JOB 的「`DELETE` 窗口 + `INSERT SELECT` 事务」保证，不依赖约束；InnoDB 隐式 rowid 作为主键。
2. **维度列全部 `NOT NULL DEFAULT ''`**：聚合 JOB 写入时 `IFNULL(col,'')` 归一，保证 GROUP BY 与过滤谓词行为对齐 Doris；维度 NOT NULL 使每行定长部分可控。
3. **维度列长度取 Doris 定义与明细表的交集**（如 `ai_apikey_id` 聚合表 128 vs 明细表 256，截断风险由聚合 SQL 侧保证口径一致）。
4. 索引围绕 `ts_min` 与排行热维度，与查询 `WHERE ts_min BETWEEN ... GROUP BY <维度>` 模式匹配。

### 4.3 聚合语义

每周期（默认 60s）对上一整分钟窗口：

```
BEGIN
  DELETE FROM bfe_ai_metrics_1m WHERE ts_min = <上一整分钟>;
  INSERT INTO bfe_ai_metrics_1m SELECT DATE_FORMAT(log_time,'%Y-%m-%d %H:%i:00'), ... 
    FROM bfe_ai_request_log
    WHERE log_time >= <上一分钟起点> AND log_time < <本分钟起点>
    GROUP BY ts_min, <全部 40 维度>;
COMMIT
```

窗口重放幂等（重复执行同一周期结果不变）；多副本 api 部署用 `GET_LOCK('report_agg_job', 0)` 抢锁防重。

## 5. 账号与权限

| 账号 | 使用者 | 权限 |
|------|--------|------|
| 写入账号（如 `report`） | log-reader `mod_log_mysql` 插件 | 报表库明细表 INSERT/UPDATE（幂等覆盖需要 UPDATE）；**无 DDL/DELETE** |
| 查询/维护账号（如 `report_rw`） | ai-gateway-api 查询 API + 聚合/分区 JOB | 报表库明细表/聚合表 SELECT、聚合表 INSERT/DELETE、明细表 DELETE（非分区降级清理）、ALTER TABLE（分区管理） |

网络策略只放通报表库端口；两账号与控制面库账号完全隔离，凭据泄露爆炸半径可控。

## 6. 演进与容量

- **列演进规则**：pb 新增字段时，明细表加列与 Doris 侧同步评估；聚合表维度/指标集合与 Doris `bfe_ai_metrics_1m` 同发布同演进（DDL 与聚合 JOB、查询代码同 PR 落地）。
- **容量建议**：MySQL 形态目标量级 ≤ 日均百万级请求；超量建议走 Doris 标准形态（批量 INSERT 压力远小于 Kafka→Doris 对 Doris 的压力，但单表 + 日分区在千万级/日会出现索引写入放大与聚合 JOB 耗时问题）。
- **清理即 DROP PARTITION**：明细与聚合表均按天分区，过期清理秒级完成；非分区形态（部分 RDS）降级 `DELETE ... LIMIT` 分批，由 JOB 自动探测适配。
