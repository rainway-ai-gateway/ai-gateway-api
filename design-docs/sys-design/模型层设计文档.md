# Rainway AI Gateway - 模型层设计文档

## 1. 概述

本文档描述 `ai-gateway-api` 当前代码实现中 `model/` 层的设计，包括子包职责、核心结构体、接口定义、事务管理、典型业务流程以及与其他层的交互方式。

模型层采用 **Manager + Storager 接口** 的分层模式：
- **Manager**：封装业务逻辑、参数校验、事务编排与级联操作。
- **Storager 接口**：定义持久化操作契约，由 `storage/rdb/` 各子包实现。
- **Param / Filter**：分别用于写入入参与查询条件，字段多为指针类型以区分“未传”与“零值”。

模型层不直接依赖底层数据库，只依赖同包或 `model/shared` 中定义的 `XxxStorager` 接口，从而实现业务逻辑与存储实现的解耦。

## 3. 通用设计模式

### 3.1 四层结构

每个业务模型基本遵循 **Param / Filter / Storager / Manager** 四层结构：

| 类型 | 说明 |
|------|------|
| `XxxParam` | 创建/更新入参，字段多为指针类型。 |
| `XxxFilter` | 查询条件，包含分页字段 `Page` / `PageSize`。 |
| `XxxStorager` | 定义持久化操作的接口。 |
| `XxxManager` | 业务逻辑实现，聚合 `itxn.TxnStorager` 与其它 `Storager`。 |

### 3.2 函数命名与参数风格

| 操作 | 命名 | 参数 | 返回值 |
|------|------|------|--------|
| 创建 | `CreateXxx(ctx, param)` | `context.Context, *XxxParam` | `(int64, error)` 或 `error` |
| 查询单条 | `FetchXxx(ctx, filter)` | `context.Context, *XxxFilter` | `(*Xxx, error)` |
| 查询列表 | `FetchXxxList(ctx, filter)` | `context.Context, *XxxFilter` | `([]*Xxx, error)` |
| 更新 | `UpdateXxx(ctx, filter, param)` | `context.Context, *XxxFilter, *XxxParam` | `(int64, error)` |
| 删除 | `DeleteXxx(ctx, filter)` | `context.Context, *XxxFilter` | `error` |
| 校验 | `validateXxx`、`CheckXxx`、`XxxBeUsed` | 视业务而定 | `error` |

分页默认值一般为 `page=1, pageSize=20`，最大 100。

### 3.3 事务管理

`model/itxn/txn.go` 定义事务抽象：

```go
type TxnStorager interface {
    AtomExecute(ctx context.Context, do func(context.Context) error) error
}
```

`storage/rdb/txn/txn.go` 提供基于 `database/sql` 的实现：

```go
func (ps *RDBTxnStorager) AtomExecute(ctx context.Context, do func(context.Context) error) error {
    dbCtx, err := ps.dbCtxFactory(ctx, lib.OpenTxn())
    if err != nil {
        return err
    }
    return lib.RDBTxnExecute(dbCtx, do)
}
```

Manager 中的业务方法通常包裹在 `AtomExecute` 中：

```go
func (m *XxxManager) CreateXxx(ctx context.Context, param *XxxParam) error {
    return m.txn.AtomExecute(ctx, func(ctx context.Context) error {
        // 1. 参数校验
        // 2. 唯一性检查
        // 3. 调用 storager 写入
        return nil
    })
}
```

若传入的 `ctx` 已经是 `*lib.DBContext`，工厂会复用同一事务，从而支持嵌套事务场景。

### 3.4 模型层与存储层交互

`model/` 只依赖同包或 `model/shared` 中的 `XxxStorager` 接口，`storage/rdb/` 各子包提供具体实现：

```go
// storage/rdb/basic/product.go
var _ ibasic.ProductStorager = &ProductStorage{}

type ProductStorage struct {
    dbCtxFactory lib.DBContextFactory
}

func NewProductStorage(dbCtxFactory lib.DBContextFactory) *ProductStorage {
    return &ProductStorage{dbCtxFactory: dbCtxFactory}

```

`stateful/container/rdb/components.go` 负责依赖注入与单例初始化：


### 3.5 适配器模式

`quota/` 子包除了定义自身的 `QuotaPlanStorager` 接口外，还通过 `NewXxxStoragerAdapter` 将 `entity.EntityStorager`、`rate_limit_policy.RateLimitPolicyStorager`、`quota.QuotaPlanStorager` 适配为 `model/shared` 中定义的通用接口，供 `APIKeyManager` / `EntityManager` 统一调用：

```go

quota.NewRateLimitPolicyStoragerAdapter(rateLimitPolicyStorager)     // 输入：rate_limit_policy.RateLimitPolicyStorager
quota.NewEntityStoragerAdapter(entityStorager)                       // 输入：entity.EntityStorager
```

### 4.25 `model/ioperlog`

操作日志模型，负责记录控制面配置变更，支持审计查询。

#### 4.25.1 核心类型

```go
// model/ioperlog/types.go
type OperationLogEntry struct {
    ID               int64
    LogID            string
    OperatorType     OperatorType // 0=user, 1=token

    ResourceType     string       // entity/api_key/provider/cluster/...
    ResourceID       string

    RequestMethod    string
    ClientIP         string
    UserAgent        string
    CreatedAt        time.Time
}

type OperationLogFilter struct {
    LogID            *string
    OperatorType     *OperatorType
    OperatorID       *int64
    OperatorName     *string
    Action           *string
    ResourceType     *string
    ResourceID       *string
    ResourceName     *string

type OperationLogStorager interface {

}

    Record(ctx context.Context, entry *OperationLogEntry)
}

type OperationLogManagerInterface interface {
    OperationLogRecorder
    SetContextExtractor(extractor ContextExtractor)
    QueryLogs(ctx context.Context, filter *OperationLogFilter) (*OperationLogQueryResult, error)
    Close() error

```

#### 4.25.2 OperationLogManager

`OperationLogManager` 采用**内存缓冲通道 + 后台批量 worker** 实现异步落库：

- 缓冲通道默认容量 `4096` 条；批量大小默认 `200` 条；flush 超时默认 `5s`。
- 调用 `Record(ctx, entry)` 时先由 `ContextExtractor` 从 `ctx` 注入 `log_id`、请求路径、客户端 IP 等请求级字段，再投递到缓冲通道。
- 缓冲满或关闭时降级为同步写入；写入失败重试 3 次，仍失败则记录 error log。
- 提供 `QueryLogs` 供 `GET /operation-logs` 查询；返回结果按 `created_at DESC` 排序。

#### 4.25.3 敏感字段脱敏

`model/ioperlog/mask.go` 提供统一脱敏函数：

```go
func MaskAPIKeyToken(token string) string
func MaskString(string) string
func MaskSensitiveFields(data map[string]interface{}) map[string]interface{}
func MaskErrorMessage(msg string, values ...string) string
```

脱敏规则：

| 字段 | 规则 |
|------|------|
| `password`、`secret`、`session_key`、`private_key`、`token`、`access_token`、`client_secret`、`secret_key`、`access_key` 等 | 替换为 `******` |
| `api_key`、`apikey`、`key`（字符串类型） | 保留前 4 位和后 4 位，中间用 `****` 替代 |
| `certificate`、`cert_body`、`private_key_body` 等 | 替换为 `[已更新]`，不记录具体内容 |
| 嵌套 map | 递归脱敏 |
| `[]interface{}` 数组 | 逐元素递归，元素为 map 时按上述规则脱敏（如 provider `keys[].key`） |
| `error_msg` 自由文本（api_key 域） | 对错误消息中已知的 API-Key 值做值级精确替换，掩码形态同 `key` 行；兜住 DAO 驱动错误等未预见回显路径（issue #185） |

各业务 Manager 在构造 `change_summary` 后调用 `MaskSensitiveFields`，确保持久化前完成脱敏。失败审计的 `error_msg` 在截断后由 api_key 域调用 `MaskErrorMessage` 做值级脱敏（issue #185）。

#### 4.25.4 接入域

第一期在以下 Manager 的写操作中接入操作日志记录：Entity / EntityType / API-Key / Provider / Cluster / RouteRule / Domain / Certificate / QuotaPlan / RateLimitPolicy / ModelPrice / User / Token。各 Manager 通过 `SetOperationLogManager` 注入 `OperationLogManager`。

每个接入域提供一个私有函数 `recordXxxOperation(ctx, action, resourceID, resourceName, parentID, before, after, err)`，其中最后一个参数 `err` 决定日志状态：

- 当 `err == nil` 时，`Status = StatusSuccess`（`1`），`ErrorMsg` 为空。
- 当 `err != nil` 时，`Status = StatusFailed`（`2`），`ErrorMsg` 为 `ioperlog.TruncateErrorMessageDefault(err)` 截断后的错误信息（不超过 `operation_logs.error_msg` 字段长度 1024）。

调用时机：

- **成功路径**：业务事务提交成功后调用，传入 `nil`。
- **失败路径**：在写操作返回错误前调用，传入具体的 `err`。例如 `ClusterManager.DeleteCluster` 在 `deleteCheckers` 返回 "route in use" 时，会立即记录一条 `status=2` 的失败日志，再向上返回错误。

该设计保证既保留成功变更的审计轨迹，也保留失败尝试的审计证据，满足 issue #117 等场景的排障需求。

校验要点：

- `provider` 必填，且必须引用 `/providers` 中已存在的 Provider；
- `models` 必填，至少 1 个元素；每个模型名必须存在于所属 Provider 的 `models` 中；
- `keys` 非必填，默认值为空数组 `[]`；
- 若 `keys` 非空，所有元素 `name` 必填且必须对应 Provider `keys` 中存在的 name，同一数组内 `name` 唯一，`weight` ∈ `[0,100]`，且所有 `weight` 之和必须等于 `100`；
- `key_policy` 若传入，`strategy` 仅允许 `weighted_random`，`max_retries`、`retry_backoff_initial`、`retry_backoff_max` 均须 `>=0`，且 `retry_backoff_max >= retry_backoff_initial`；

- `price_miss_action` 若传入，取值仅支持 `fallback_chat`、`bill_zero`、`reject`；省略等价 `fallback_chat`；控制台新建集群显式落值，校验规则与 BFE `AIConfCheck` 同源（issue #1479）；
- `match_prefix` 非必填，若传入且非空则必须以 `/` 结尾；
- `strip_prefix` 为 `true` 时，`match_prefix` 必填且非空。

#### Cluster 配置导出（AIConf）

`model/icluster_conf/exporter.go` 在导出 `server_data_conf` 时，将 `LLMConfig` 映射为 BFE `AIConf` 结构。Provider 与 Cluster 分离后，`AIConf` 的实例池来自 Provider、`Keys` 通过按 `name` join Provider 的 key 明文与 Cluster 的 key 权重生成：

> **敏感字段加密（2026-10-05 立项）**：`[Security].EncryptExports=true` 时，导出组装完成后
> `AIConf.Keys[].Key` 以 `enc$v1$` 字段级密文下发（同 mod-api-key 信封规范），BFE 加载时
> 经 `bfe.conf [Security]` keyring 解密进内存；`Name`/`Weight`/`KeyPolicy` 等非敏感字段
> 原样。详见 `design-docs/modifications/2026-10-05-export-config-field-encryption/`。

```go
type AIKey struct {
```

导出逻辑：

1. 根据 `cluster.LLMConfig.Provider` 查询 Provider，读取 `instance_pool` 生成 BFE 实例池/子集群/集群配置（结构与原 cluster 直接持有 `instance_pool` 时一致）。
2. 根据 `cluster.LLMConfig.Keys` 中的 `name`，从 Provider `keys` 中查找对应 `key` 明文，按 `weight` 组装为 `AIConf.Keys`。
3. 将 Provider 的 `model_protocols` 原样透传到 `AIConf.ModelProtocols`，供 BFE 判断请求协议风格是否被当前集群支持。若 Provider 未设置 `model_protocols`，`AIConf.ModelProtocols` 为空数组，BFE 兜底为仅支持 `openai`。
4. 将 Provider 的 `protocol_paths` 原样透传到 `AIConf.ProtocolPaths`，供 BFE 按检测协议改写上游路径（仅标准入口 `/v1/...` 生效，未配置即透传）。校验（键 ⊆ `model_protocols` 且 ∈ {openai, anthropic}、值路径格式）在 provider 创建/更新时完成，BFE 加载期另有 key 白名单兜底校验。
5. 若 `Provider` 非空：
   - 读取 Provider 的 `time_zone` 和 `tiers`，填充到 `AIConf.ModelTable.TimeZone` / `Tiers`；`time_zone` 为空时默认 `"Asia/Shanghai"`；`tiers` 为空时 `Tiers` 为空数组。
   - 调用 `model/imodel_price` 按 `provider` 查询 `model_prices` 记录，将 `prices` 和 `tier_prices` 分别填充到 `AIConf.ModelTable.Models[].Prices` / `TierPrices`。
   - `Currency` 固定填充为 `"RMB"`。
   - 若 `Provider` 为空或该 provider 无记录，`ModelTable.Models` 为空列表。

`model_prices` 变更不会同步触发 InnerAPI 推送，由 BFE/Conf Agent 按自身周期拉取配置。

#### Cluster EPP 调度相关改造

EPP（llm-d 调度器）接入后，`model/icluster_conf/cluster.go` 承担以下改造点：

- `Cluster` 结构体新增 `balance_mode`（varchar，默认 `WRR`，取值 `WRR`/`EPP`）与 `epp_config`（JSON text，简化用户形态）两字段。`balance_mode` 是 EPP 模式的**唯一判定来源**：`getBalanceMode()` 直读该字段，原 pool `Role` 派生逻辑已删除；创建流程按 `balance_mode` 生成 `Role=COMMON`/`Role=EPP` 的 pool。
- `epp_config` 非空即须通过字段校验（与 `balance_mode` 无关）；`balance_mode=EPP` 时必填并生效，`WRR` 时保留休眠（不编译、不导出，切换模式不丢配置）。校验规则内聚在 cluster 创建/更新路径（`balance_mode=EPP` 缺 `epp_config` 返回 422）。
- EPPAddr 生成由静态派生（旧 `pools.epp_server`）改为**分配驱动**：`balance_mode=EPP` 且有有效分配时，按 `epp_assignments` 生成有序 `GslbBasic.EPPAddr [主, 备]`（host/port 经 `net.JoinHostPort` 拼接）；无有效分配时**降级导出**——该 cluster `BalanceMode` 置为 `WRR`、不生成 `EPPAddr`，同时输出 error 级日志（含 cluster 名与原因），不阻塞整份 server_data_conf 下发。降级与 EPPAddr 生成逻辑位于 `model/iroute_conf/exporter.go` 的 server_data_conf 导出路径。

`APIKeyManager.CreateAPIKey` 核心流程：

```go
func (m *APIKeyManager) CreateAPIKey(ctx context.Context, param *APIKeyParam) error {
    return m.txn.AtomExecute(ctx, func(ctx context.Context) error {
        // 1. 检查同产品下 ID 是否重复
        list, err := m.storager.FetchAPIKeyList(ctx, &APIKeyFilter{
            ID: param.ID,
            ProductName: param.ProductName,
        })
        if err != nil {
            return err
        }
        if len(list) > 0 {
            return xerror.WrapParamErrorWithMsg(fmt.Sprintf("Duplicate id with product:%s", *param.ProductName))
        }

        // 2. 验证 Entity（如果指定）
        if param.EntityID != nil && *param.EntityID != "" && m.entityStorager != nil {
            entity, err := m.entityStorager.FetchEntity(ctx, &shared.EntityFilter{EntityID: param.EntityID})
            if err != nil {
                return err
            }
            if entity == nil {
                return xerror.WrapParamErrorWithMsg(fmt.Sprintf("Entity not found: %s", *param.EntityID))
            }
        }

        // 3. 创建 QuotaPlan（如果有）
        if param.QuotaPlan != nil && m.quotaPlanStorager != nil {
            quotaPlanID, err := m.quotaPlanStorager.CreateQuotaPlan(ctx, param.QuotaPlan)
            if err != nil {
                return err
            }
            param.QuotaPlanID = &quotaPlanID
        }

        // 4. 创建 RateLimitPolicy（如果有）
        if param.RateLimitPolicy != nil && m.rateLimitPolicyStorager != nil {
            rateLimitPolicyID, err := m.rateLimitPolicyStorager.CreateRateLimitPolicy(ctx, param.RateLimitPolicy)
            if err != nil {
                return err
            }
            param.RateLimitPolicyID = &rateLimitPolicyID
        }

        // 5. 创建 RouteRules（如果有）
        if param.RouteRules != nil && m.routeRulesStorager != nil {
            routeRulesID, err := m.routeRulesStorager.CreateRouteRules(
                ctx, shared.RouteRulesTypeAPIKey, param.Key, param.RouteRules)
            if err != nil {
                return err
            }
            param.RouteRulesID = &routeRulesID
        }

        // 6. 创建 APIKey
        _, err = m.storager.CreateAPIKey(ctx, param)
        return err
    })
    if err != nil {
        return err
    }

    // 7. 同步 Redis 剩余量（事务外，最终一致；失败不影响 DB 已提交结果）
    if param.Key != nil && param.QuotaPlan != nil &&
        (param.QuotaPlan.Unlimited == nil || !*param.QuotaPlan.Unlimited) &&
        param.QuotaPlan.Quota != nil && m.quotaCache != nil {
        if err := m.quotaCache.SetRemaining(ctx, *param.Key, param.QuotaPlan.Quota, param.QuotaPlan.Unit); err != nil {
            // 记录日志，不阻塞接口返回
            stateful.AccessLogger.Warn("failed to set quota cache for api_key %s: %v", *param.Key, err)
        }
    }
    return nil
}
```

`APIKeyManager.CreateAPIKey` 新增对传入 `key` 的全局唯一性校验（覆盖 `api_keys.api_key` 与 `api_key_tokens.api_key`），若冲突返回 422。

`APIKeyManager.DeleteAPIKey` 会级联删除 `quota_plan`、`rate_limit_policy`、`route_rules`，最后删除 `api_key`；级联删除的嵌套资源经 Auditor 记录 `quota_plan/delete`、`rate_limit_policy/delete` 审计日志，`resource_parent_id` 为该 API Key 的业务 ID（issue #161）。

#### 4.4.2 CRUD 操作

`ModelPriceManager` 提供与通用模型一致的 CRUD：

- `CreateModelPrice`：新增单条记录，校验必填字段与唯一键；`provider` 不强制引用已存在的 Provider；`price_currency` 由系统固定填充为 `RMB`；若携带 `tier_prices`，校验 tier name（**初期只支持 `peak`**）及内部价格键名。
- `FetchModelPrice` / `FetchModelPriceList`：支持按 `id` 或 `(provider, model, mode)` 查询单条；列表查询支持按 `provider`、`mode` 分页过滤。
- `UpdateModelPrice`：支持部分字段更新，未传字段保持原值；按 `id` 或 `(provider, model, mode)` 定位记录；`provider` 更新时不校验存在性。
- `DeleteModelPrice`：按 `id` 或 `(provider, model, mode)` 删除。
- `ListProviders`：返回 `model_prices` 表中所有 `provider` 名称的去重列表，按字典序排列。

校验要点：

- `provider`、`model`、`base_model`、`mode` 必填；
- `provider` 仅作为价格归集标识，不强制引用 `/providers` 中已存在的 Provider；
- `(provider, model, mode)` 不能重复；
- `prices` 必填且至少包含一个价格字段，所有价格字段非负；价格支持科学计数法与十进制表示法（等价合法，按 float64 解析），且折算 `价格 × 1e8` 不得超过 2^53（约 9e15，保证下游 BFE 浮点成本计算不丢失整数精确性）；
- `tier_prices` 非必填；若传入，tier name **初期只支持 `peak`**，内部价格键名须为 `prices` 枚举，所有 tier 价格字段非负并适用同样的表示法与精度上限校验；
- `mode` 必须取自预定义枚举；
- `capabilities`、`supported_parameters`、`limits`、`prices`、`tier_prices.<tier>`、`metadata` 的元素/键名必须取自对应枚举（非枚举值不可接受）。

#### 4.4.3 YAML 导入逻辑

`POST /v1/model-prices/import` 通过 `multipart/form-data` 上传 `model-list.yaml`：

```go
// model/imodel_price/import.go
type ImportMode string

const (
    ImportModeReplace ImportMode = "replace" // 全量替换：先清空 model_prices，再写入
    ImportModeMerge   ImportMode = "merge"   // 增量合并：更新已有记录，插入新记录
)

type ImportResult struct {
    ImportedCount int      `json:"imported_count"`
    SkippedCount  int      `json:"skipped_count"`
    Errors        []string `json:"errors"`
}
```

处理流程：

1. 解析 YAML，校验 `version` 与 `default_currency`（必须为 `RMB`）；YAML 数字字面量支持科学计数法（如 `7.6234102728e-08`），按 float64 解析；
2. 校验每条记录的 `(provider, model, mode)` 唯一性；
3. 校验必填字段：`provider`、`model`、`base_model`、`mode`、`prices`；
4. 校验 `prices` 中至少包含一个价格字段且所有价格字段非负、折算 `价格 × 1e8` 小于 2^53；
5. 若记录包含 `tier_prices`：校验 tier name（**初期只支持 `peak`**），内部价格键名须为 `prices` 枚举，所有 tier 价格字段非负并适用同样的精度上限校验；
6. `replace` 模式：清空 `model_prices` 表后批量写入；
7. `merge` 模式：对已有 `(provider, model, mode)` 记录执行更新，新增记录执行插入。

> 说明：v0.4 仅支持人民币（RMB），不扩展美元、欧元等多币种。
>
> 说明（v0.6）：价格 JSON 序列化回归标准编码器，导出文本中极小值可能以科学计数法出现（如 `1.5e-6`），与十进制表示法等价；issue-102 引入的十进制定制序列化已删除，详见 `design-docs/modifications/2026-09-08-model-price-scientific-notation/`。

#### 4.4.6 批量价展开（2026-10-07，批量与异步任务支持一期）

- `mode` 白名单新增 `batch`；`file` 不进价格体系（文件操作不计费，数据面对 ModeFile 请求不做查价）。
- `ModelPriceParam` 新增可选 `batch_discount`（(0, 1]，默认 0.5）：语义为"导出时把本行各 token 价格键 × 系数展开生成 `(provider, model, mode=batch)` 价格行"；`tier_prices` 同规则展开。
- **折扣在导出时展开而非数据面运行时计算**：`newAIConf` 组装 `AIConf.ModelTable` 时生成 batch 行一并下发，数据面 `LookupModelPrice(cluster, model, "batch")` 纯查表，查价 miss 计 0 费 + `PriceLookupMiss` 计数，不回退 chat 价。
- **覆盖机制**：手工维护的 `(provider, model, mode=batch)` 行优先于系数展开行；导出时检测冲突，手工行优先并记录告警日志。
- 报表口径：报表库同时存在 chat/batch 两行价，"批量节省金额" = (chat 价 − batch 价) × usage，在报表 SQL 层派生（`batch_savings` 派生指标）。

```go
                return err
            }

            if err != nil {
                return err
            }
            rateLimitPolicyID = &id

        param.RateLimitPolicyID = rateLimitPolicyID
        param.RouteRulesID = routeRulesID
        _, err := m.storager.CreateEntity(ctx, param)

    })
```

```go
func (m *QuotaPlanManager) ResetBalance(ctx context.Context, planID int64, newQuota *float64, updateLastResetAt bool) error {
    return m.txn.AtomExecute(ctx, func(ctx context.Context) error {
        plan, err := m.storager.FetchQuotaPlan(ctx, &QuotaPlanFilter{ID: &planID})
        if err != nil {
            return err
        }
        if plan == nil {
            return fmt.Errorf("quota_plan not found")
        }

        // 无限配额无 balance 可 reset：语义错误定型为 PARAM → 422 Param Illegal（issue #183），
        // 不得为裸 error 被框架兜底为 500 Unknown Exception。
        if plan.Unlimited != nil && *plan.Unlimited {
            return xerror.WrapParamErrorWithMsg("cannot reset balance for unlimited quota")
        }

        resetQuota := plan.Quota
        updateParam := &QuotaPlanParam{}
        if newQuota != nil {
            resetQuota = newQuota
            updateParam.Quota = resetQuota
        }

        now := time.Now()
        if updateLastResetAt {
            updateParam.LastResetAt = &now
        }

        _, err = m.storager.UpdateQuotaPlan(ctx, &QuotaPlanFilter{ID: &planID}, updateParam)
        return err
    })
}
```

`updateLastResetAt=true` 用于定时调度；`false` 用于手动重置接口，避免影响调度判断。

手动重置（`updateLastResetAt=false`）的失败错误语义（issue #183）：目标计划 `unlimited=true` 时返回 422 `Param Illegal: cannot reset balance for unlimited quota`（`xerror` 的 PARAM 类型映射），不产生配额变更，并在事务返回后记录 `quota_plan/reset`、`status=2`、error_msg 非空、`resource_parent_id` 为 owner 业务 ID 的操作日志（SC2101-TC047 断言 3）。裸 error 会被 `xerror.Resolve` 兜底为 500 Unknown Exception，禁止用于确定性语义错误。

- 释放/续期时校验 token，防止误删他人锁；
- 未获取锁的实例直接跳过本次调度。

### 4.11 `model/quotacache`

`model/quotacache` 是本次新增的独立包，用于封装 API-Key / Entity 的实时配额 Redis 缓存操作。该包的引入是为了将原本散落在 `endpoints/openapi_v1` 中的 Redis 操作下沉到 model 层，使端点层只负责 HTTP 参数解析与 model 调用。

#### 4.11.1 接口定义

```go
// model/quotacache/quotacache.go
package quotacache

import "context"

// QuotaCache 封装 API-Key / Entity 的实时配额缓存操作。
type QuotaCache interface {
    // GetRemaining 获取指定对象的实时剩余配额（已按 unit 转换为浮点数）。
    GetRemaining(ctx context.Context, key string, unit *string) (float64, error)

    // BatchGetRemaining 批量获取指定对象的实时剩余配额。
    BatchGetRemaining(ctx context.Context, keys []string, unit *string) (map[string]float64, error)

    // SetRemaining 将指定对象的 Redis 剩余量设置为 target。
    // 内部使用 IncrBy(delta)，适用于需要保留 used 的配额调整场景。
    SetRemaining(ctx context.Context, key string, quota *float64, unit *string) error

    // ResetToQuota 将 Redis 剩余量重置为 quota 总量。
    // 内部复用 SetRemaining，使用 IncrBy(delta)。
    ResetToQuota(ctx context.Context, key string, quota *float64, unit *string) error

    // ResetToQuotaAtomic 将 Redis 剩余量原子地覆盖为 quota 总量。
    // 内部使用 Lua + SET，不依赖当前值，专用于周期重置。
    ResetToQuotaAtomic(ctx context.Context, key string, quota *float64, unit *string) error

    // DeleteKeys 删除指定对象的 Redis 配额 Key。
    DeleteKeys(ctx context.Context, keys []string) error
}
```

#### 4.11.2 Redis 实现

```go
// model/quotacache/redis.go
package quotacache

import (
    "context"
    "strings"

    golibquota "github.com/bfenetworks/go-lib/quota"
    "github.com/bfenetworks/bfe/bfe_util/redis_client"
    "github.com/rainway-ai-gateway/ai-gateway-api/stateful"
)

type redisQuotaCache struct {
    client          redis_client.Client
    setQuotaScript  *redis_client.Script  // 缓存 Lua 脚本对象
}

func NewRedisQuotaCache(client redis_client.Client) QuotaCache {
    c := &redisQuotaCache{client: client}
    if client != nil {
        c.setQuotaScript = client.NewScript(`
            redis.call('set', KEYS[1], ARGV[1])
            return 1
        `)
    }
    return c
}

func (c *redisQuotaCache) GetRemaining(ctx context.Context, key string, unit *string) (float64, error) {
    if c.client == nil {
        return 0, nil
    }
    redisKey := stateful.AIUsedQuotaKey(key)
    remain, err := c.client.GetInt64(redisKey)
    if err != nil {
        if strings.Contains(err.Error(), "redigo: nil returned") {
            return 0, nil
        }
        return 0, err
    }
    return golibquota.PtrFromRedisValue(&remain, unit), nil
}

func (c *redisQuotaCache) SetRemaining(ctx context.Context, key string, quotaValue *float64, unit *string) error {
    if c.client == nil || quotaValue == nil {
        return nil
    }
    redisKey := stateful.AIUsedQuotaKey(key)
    targetValue := golibquota.PtrToRedisValue(quotaValue, unit)
    currentValue, err := c.client.GetInt64(redisKey)
    if err != nil {
        if !strings.Contains(err.Error(), "redigo: nil returned") {
            return err
        }
        currentValue = 0
    }
    delta := targetValue - currentValue
    _, err = c.client.IncrBy(redisKey, delta)
    return err
}

func (c *redisQuotaCache) ResetToQuota(ctx context.Context, key string, quotaValue *float64, unit *string) error {
    return c.SetRemaining(ctx, key, quotaValue, unit)
}

func (c *redisQuotaCache) ResetToQuotaAtomic(ctx context.Context, key string, quotaValue *float64, unit *string) error {
    if c.client == nil || quotaValue == nil {
        return nil
    }
    redisKey := stateful.AIUsedQuotaKey(key)
    targetValue := golibquota.PtrToRedisValue(quotaValue, unit)
    _, err := c.setQuotaScript.Run(redisKey, targetValue)
    return err
}
```

### 4.14 Provider 与模型访问协议

Provider 独立为 `/providers` 资源后，原 `/model-provider-types` 与 `/tools/get-models-from-provider` 能力被整合：模型访问协议枚举作为 `providers.model_protocols` 的合法性约束在 `providers.md` 中定义；模型发现通过独立的无状态工具接口 `/providers/tools/discover-models` 触发。

- **`/providers`**：独立资源，集中管理模型提供方的接入能力（`model_endpoint`、`models`、`keys`、`instance_pool`、`model_protocols`、`protocol_paths`）。
- **`/providers/tools/discover-models`**：接收 `model_protocol`、`schema`、`addr`、`port`、`uri`、`apikey` 参数，按 `model_protocol` 生成认证头并选择响应解析器，返回模型名列表；不读写 Provider 资源。

Provider 管理不影响 InnerAPI 导出配置的结构，仅改变 `AIConf` 内部生成方式：实例池与 key 明文从 Provider 获取，Cluster 只保留转发策略；同时把 Provider 的 `model_protocols` 透传为 `AIConf.ModelProtocols`、`protocol_paths` 透传为 `AIConf.ProtocolPaths`。

**实例供给模型（`instance_source`）**

K8s 服务发现场景下，Provider 增加三个字段声明实例供给方式（详见 [providers.md](../api-define/OpenAPI接口定义/providers.md)）：

| 字段 | 说明 |
|------|------|
| `instance_source` | 实例供给方式，枚举 `instance_pool`（人维护，默认）/ `k8s_pool`（K8s 发现组件经 InnerAPI `/k8s_pools` 维护）；P0 仅接受 `instance_pool`（`k8s_pool` 返回 422），P1 放开枚举 |
| `k8s_pool_name` | `instance_source=k8s_pool` 时必填，普通名称校验，与 K8s Service 名无耦合；`instance_pool` 模式下休眠保留、不生效，切回 `k8s_pool` 模式时自动恢复生效 |
| `k8s_instance_pool` | 只读镜像，系统从 `/k8s_pools` 同步，请求携带即 422 |

**有效池（effective pool）** 是 Provider 对下游暴露的唯一实例口径：

```
有效池 = instance_source == "k8s_pool" ? k8s_instance_pool : instance_pool
```

`model/iprovider` 导出的 `iprovider.EffectiveInstancePool` 被统一消费：cluster 创建引用 provider 时的 pool/sub-cluster 快照、provider 更新时同步引用 cluster 派生池（`ProviderInstancePoolSyncer`）、实例池相等比较一律改读有效池。`instance_pool` 与 `k8s_pool_name` 呈休眠对称语义：各自在非激活模式下保留原值、不参与校验与同步，切回激活模式时自动恢复生效（`instance_pool` 在 `k8s_pool` 模式下作为人工兜底）。

syncer 空池语义：删除 syncer 对空池的早退，有效池为空时同步清空引用 cluster 的派生池（含空列表）；空池数据面行为为导出空条目、BFE 加载接受、该 cluster 请求 500（`BK_NO_BACKEND`），由告警覆盖。Provider 实例池校验（≥1、`(addr,port)` 去重、≥1 个 `weight>0`）在 `instance_pool` 模式下原封不动，`k8s_pool` 模式下 `instance_pool` 不参与校验，合法空池只出现在 `k8s_pool` 模式。

### 4.15 `model/epp_pool`

EPP 调度对接模型，承担 EPP（llm-d 调度器）控制面职责：实例池读写、cluster→实例组分配、epp_data 导出。

- **实例池管理**：`/epp-pool` 单例池（池名由配置项 `RunTime.DefaultEPPInstancePoolName` 提供，默认 `EPP.pool`）的读写字段模型；`PATCH` 全量替换（组 + 实例两级）展开写入 `epp_instances`，校验组名唯一、实例 id 池内全局唯一、`(host, port)` 组合唯一、组规模为每组恰好 1 实例（拒绝空组与 2 个及以上实例的组）。
- **分配器**：贪心 + 字典序 tie-break（组负载最小优先、并列取组名字典序最小；组内 primary 负载最少优先、并列取实例 id 字典序最小），全程确定性、可重放。触发点：cluster 创建/`WRR → EPP` 变更时同步自动分配；`/epp-pool` PATCH 后悬空修复（同组重选 primary 或跨组重分配）；30s 周期对账 reconciler（可配，幂等）。`PUT /epp-assignments/{cluster}` 手工覆写作为运维兜底。
- **epp_data generator**：生成 `ConfigTopicEppData` topic 的两段配置——`epp_config` 段（`balance_mode=EPP` 的 cluster → 编译后 `EndpointPickerConfig`）与 `assignment` 段（cluster → `{group}` 映射，`epp_assignments` 只存 cluster → group，分配粒度为组）；单 topic 两段合并保证同一 version 原子快照，复用 `model/iversion_control` 的 `ExportConfig` 框架。
- **epp_config 编译**：把 `clusters.epp_config` 的简化用户形态（调度档位 + 一等公民调优参数 + 流控）**确定性编译**为完整 `EndpointPickerConfig`（档位权重映射、亲和 scorer 条件注入、flowControl 段展开、featureGates 追加、固定插件注入），编译规则固化并单测覆盖；仅 `balance_mode=EPP` 时编译下发，WRR 时休眠保留。

### 4.16 `model/ik8s_pool`

K8s 实例池域，承担 `/k8s_pools` InnerAPI 四端点对应的模型层能力：发现组件写入实例快照，引用该池的 provider 刷新只读镜像并同步下游 cluster 派生池。接口契约见 [k8s-pools.md](../api-define/InnerAPI接口定义/k8s-pools.md)。

- **资源模型**：`k8s_pools` 表（`name` 唯一键、`instances` JSON、`created_at`/`updated_at`）；`name` 为普通名称校验，与 K8s Service 名无耦合。池与 provider 允许 N：1——实例列表只存一份，provider 侧 `k8s_instance_pool` 为只读镜像；provider 可引用尚不存在的 pool（池不存在 ≡ 零实例）。
- **manager 方法**：`ReplaceInstances`（全量替换、幂等 upsert，条目不存在则创建）、`FetchPool`、`FetchPoolList`、`DeletePool`，对应四端点；GET 响应附带 `instance_count` 与 `last_sync_time`（取行 `updated_at`）。
- **同步事务 fan-out**（PUT 与 DELETE 共用，在 `itxn` 单事务内）：
  1. 写 `k8s_pools` 行（PUT 更新 instances / DELETE 删行）；
  2. 查出所有 `instance_source=k8s_pool && k8s_pool_name==name` 的 provider；
  3. 逐个刷新其 `k8s_instance_pool`（PUT → 新列表；DELETE → 空列表）；
  4. 逐个触发各自 cluster 派生池同步——复用从 `ProviderInstancePoolSyncer` 抽出的 `ClusterManager.SyncProviderEffectivePool`；
  5. cluster_table version 由 `ExportConfig` MD5 签名机制在下次导出自动 bump。

  任一步失败整个事务回滚。DELETE 为**无引用保护**语义：被引用的 pool 允许删除，引用者镜像置空、cluster 派生池清空（事务内）；provider 视角下"池不存在"与"池存在但零实例"是同一状态。
- **依赖注入**：manager 依赖 `itxn.TxnStorager`、provider storager、`ClusterManager`，禁直连 `stateful.Default*`。

- **导出生成**：`ConfigExport` + `IntentConfigGenerator`，topic 常量 `ConfigTopicIntentConfig = "intent_config"` 定义在本包内；generator `Fetch` 当前行（无记录返回 nil，不导出，BFE 维持现状）、组装 `IntentConfigDataExport{Version, MinConfidence, Questions(RawMessage)}`——**Data 即 `intent_questions.data` 文件内容原样**（Version 内嵌文件，同 ai-route 端点形态，非 ai-cache 的 `Config` 包装形态），走 `iversion_control.ExportConfig` 标准流程（MD5 签名 + `config_versions` 版本比对）。

### 4.26 `model/ibatch`

批量任务管控与对账模型（2026-10-07 新增，批量与异步任务支持一期），对应 `batch_tasks` / `batch_files` 两表。承载 provider 原生 OpenAI Batch API 任务在控制面的权威实体：任务查询（DB 优先、Redis `BATCH_TASK` 回源兜底）、cancel（控制面直调 provider）、周期性对账 job。数据面落地方案见 BFE `mod_ai_batch`，接口见 `endpoints/openapi_v1/batches/`；完整机制见 [details/批量任务与对账.md](./details/批量任务与对账.md)。

```go

    operationLog ioperlog.OperationLogRecorder

```

- **任务查询（DB 优先、Redis 回源兜底）**：详情查询先查 `batch_tasks`，miss 时回源 Redis `BATCH_TASK:<batch_id>`（覆盖 job 落库前窗口），再 miss 返回 404；列表查询走 DB 索引列 + 主键游标分页，`product_name` 为服务端解析的默认产品线（`AIRouteInnerProductName`，不接受外部传参；2026-10-23 经 issue #276 校准，原"中间件强制注入"表述被取代，见 `modifications/2026-10-23-issue-276-batch-product-name-contract-fix/`）；Redis 与 BFE 共享，BFE 结算/释放时已把 `usage_*` / `settle_*` 原地更新进 `BATCH_TASK` hash，job 同步后 DB 为权威视图。
- **cancel 五步**：查任务（DB → Redis 回源）→ 按 `provider` + `key_name` 取 key 明文与实例地址（复用 provider 组件与 `protocol_paths.openai` 拼地址）→ 出网 POST provider cancel（不可达 502 / provider 404 透传 / 其他错误透传）→ DB 条件更新抢占（`ClaimCancel`，affected_rows=0 → 409 `BATCH_TERMINAL_OR_CONFLICT`）+ Redis 幂等释放预留 → `operation_logs` 审计（change_summary 带 batch_id 与前后状态）。
- **预留-结算-释放三态**：`settle_status` 为对账主字段（`reserved`/`settled`/`released`，1e-8 定点 RMB）。数据面创建时预留（行数 × 预估 token 上限 × batch 价），下载拦截按结果文件 usage 实结（允许透支 + `over_reserved` 标记）；cancel/expired/failed 整额释放。控制面仅经兜底结算推进 `reserved → settled/released`，且一律 `WHERE settle_status='reserved'` 条件更新 + Redis `BATCH_SETTLED` 幂等锁，防双倍结算。
- **对账 job（`job.go`，每分钟 tick）**：复用 `storage/mysqlreport/job.go` 的 named lock + 循环框架（MySQL `GET_LOCK` 多副本互斥；SQLite 模式锁退化为空操作、约定单实例）。五职责：① SCAN Redis `BATCH_TASK:*` / `BATCH_FILE:*` 幂等 upsert 落库（键 TTL 48h ≫ 同步周期，无丢失窗口；**不读报表库**——报表后端可插拔，不作管控链路依赖）；② 非终态任务直调 provider `GET /v1/batches/{id}` 推进状态、补登记输出文件；③ 兜底结算（completed 且 `settle_status='reserved'` 超 30min 宽限 → 下载输出文件解析 usage 直写 Redis 结算 + 条件更新 `settled`；终态无结果文件 → `released`）；④ 对账巡检（`BATCH_RESERVE` 占用 vs DB 在途总额、`settle_units` 与日志后端 batch 成本抽样比对、日志补登 `sync_source='log'` + 告警）；⑤ 终态任务 TTL 清理（保留 N 天，retention 可配）。
- **多实例协调全部外置**：cancel 用 DB 条件更新抢占；job 用 named lock；结算/释放用 Redis 原子锁（Lua）+ DB 条件更新——锁失效双跑时全部写操作幂等收敛，最坏重复一次幂等操作，不双倍结算。进程内不保留批量任务状态。
- **降级路径**：不允许出网的部署（cancel 与兜底结算共用出网能力）降级——cancel 退化为仅展示，兜底结算退化为只依赖下载拦截 + 预留 TTL 释放（对账精度下降，部署文档标注）。
- **依赖注入**：storager、Redis 读接口、provider 出网 client、审计 recorder 均构造函数注入，可 mock（手写 callback fakes 惯例，model 覆盖率 ≥70%）。

## 5. 典型业务流程

### 5.1 API Key 创建流程

1. Endpoint 通过 `container.APIKeyIDGenerator` 从 `api_key_id_seq` 表原子分配序号，生成 `api-key-{seq}` 形式的 ID；同时生成 `{productName}-{random}` 形式的 Key。
2. 填充默认 `QuotaPlan`、`RateLimitPolicy`、`RouteRules`。
3. `APIKeyManager.CreateAPIKey` 在事务中：
   - 校验同产品下 ID 唯一。
   - 校验 `entity_id` 存在。
   - 创建 `QuotaPlan`。
   - 创建 `RateLimitPolicy`。
   - 创建 `RouteRules`。
   - 插入 `api_key` 记录。
4. 事务提交后，若配额有限，通过 `quotaCache.SetRemaining` 向 Redis 写入初始剩余量。

### 5.2 API Key 查询流程

1. `APIKeyManager.FetchAPIKey(ctx, filter)` 在事务中调用 `storager.FetchAPIKeyList`。
2. `populateAssociatedData` 依次填充：
   - `QuotaPlan`（余额通过 `quotaCache.GetRemaining` 实时读取 Redis）
   - `RateLimitPolicy`
   - `RouteRules`
   - `Entity`

### 5.3 API Key 删除流程

1. 查询待删除记录。
2. 级联删除 `quota_plan`、`rate_limit_policy`、`route_rules`。
3. 删除 `api_key` 记录。
4. 事务提交后，调用 `quotaCache.DeleteKeys` 删除对应 Redis Key。

### 5.4 Entity 创建流程

与 API Key 类似，但额外校验：
- `EntityType` 存在。
- 父 Entity 存在且父层级高于子层级。

ID 生成方式与 API Key 一致：Endpoint 在 `param.EntityID` 为空时，通过 `container.EntityIDGenerator` 从 `entity_id_seq` 表原子分配序号，生成 `entity-{seq}` 形式的 ID。已分配序号永久消耗，删除 Entity 后不回退，保证旧 ID 不会被新 Entity 复用（避免 ABA 身份混淆）。显式传入 `entity_id` 时保留查重保护（重复返回 422），`uk_entity_id` 唯一索引作为最终一致性防线。

### 5.5 配额余额重置流程

1. `QuotaPlanManager.ResetBalance(ctx, planID, newQuota, updateLastResetAt)`。
2. 不支持 `unlimited` 计划重置。
3. 若传入 `newQuota`，同时更新 `quota_plan.quota`。
4. 更新 `quota_plans.last_reset_at`（当 `updateLastResetAt=true` 时）。
5. 调用方负责通过 `QuotaCache.ResetToQuota` 重置 Redis 剩余量。

### 5.6 路由规则全量更新流程

1. `RouteRulesManager.UpdateRouteRules(ctx, ruleType, owner, param)`。
2. 校验规则参数。
3. 查询现有规则；不存在则创建，存在则按 ID 全量更新。

### 5.7 产品级路由规则 Upsert 流程

1. `RouteRuleManager.UpsertProductRule(ctx, productID, rule)`。
2. 事务中查询并加锁（`SELECT ... FOR UPDATE`）。
3. 删除该产品下所有基础/高级规则。
4. 重新批量插入新规则。
